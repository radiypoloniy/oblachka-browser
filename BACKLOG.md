## A. AI-КОНЦЕПЦИЯ (зафиксировать — было проговорено, но не записано)

Переосмыслено на основе РЕАЛЬНОГО теста железа (RTX 2070, 8GB): Gemma 4 e4b ~39 t/s —
скорость норм, но для рассуждений/чата ТУПАЯ. Вывод: «умный чат» на локальной модели
разочарует, ставить его центром хаба — нечестно.

- **Локальный AI = обработка текста + embeddings**, НЕ генеративный чат:
  - Перевод (см. ниже) — узкая задача, «не требует ума, требует обработки».
  - Embeddings (семантический поиск, умные вкладки, «похожие») — «золотой путь»,
    бесплатно и локально. Embeddings ≠ дорого (ранее путали); дорого только генерация
    текста и платные RSS-сервисы.
- **Генерация / умный чат (тип А)** — локальная слаба → облако опцией через API-ключ,
  для энтузиастов, НЕ обязаловка и не главная фича. Вернётся на хаб опцией на Этапе 5.
- **Хаб переосмыслен**: центр = навигация (омнибокс) + часто посещаемые из истории.
  Чат-фасад «Спросите что угодно» УБРАН как преждевременный (уже сделано).
- Целиться в фичи на бюджетном железе ~RTX 2070/8GB = доступно большинству.

### Два AI-рантайма (НЕ дублировать, осознанно разделить слоты инференса)
1. **transformers.js (ONNX)** — embeddings + перевод. Основной локальный слот.
2. **node-llama-cpp (GGUF)** — опциональная генерация (тип А), энтузиастам. Отдельно.

⚠️ Любой инференс — в WORKER-потоке/utility process, НЕ в main. Иначе фриз окна.
Ленивая загрузка модели с индикатором, кэш на диск.

## A2. ПЕРЕВОД (дизайн для Этапа 5, в код не сейчас)

- НЕ Gemma и НЕ embeddings. Перевод — генеративная seq2seq, но УЗКАЯ специализированная
  модель: **Opus-MT (Helsinki-NLP)** для en↔ru (своя пара, десятки МБ, быстро) или
  **NLLB distilled** (200 языков, 600M). Качество en↔ru у Opus-MT выше Gemma и быстрее.
- Формат — ONNX/transformers.js, НЕ GGUF → через node-llama-cpp не пойдёт. Отдельный
  рантайм (тот же transformers.js, что и embeddings).
- **Ступень А (брать первой, безопасно):** перевод ВЫДЕЛЕНИЯ. ПКМ → «Перевести» →
  результат в поповере/панели. Текст берётся из `selectionText` контекстного меню —
  НЕ инъекция в DOM. Риск низкий.
- **Ступень Б (отложить):** перевод ВСЕЙ страницы in-place. Инъекция в чужой DOM, гонки
  с динамическим контентом, ломает SPA-сайты. Отдельный заход с проработкой стратегии.
- ⚠️ Результат показывать в chrome-зоне (панель), НЕ поповером над WebContentsView в
  первой версии (слоёная грабля). Поповер у выделения — полировка позже, через тот же
  механizm оверлеев, что у FindBar/дропдауна омнибокса.
- ⚠️ Первая загрузка модели подвиснет молча → индикатор + ленивая загрузка по первому
  вызову (не на старте). Инференс в worker.

## B. БЛИЖАЙШИЙ ПЛАН (до сайдбара) — порядок

1. **Менеджер загрузок**
2. **Разрешения сайтов (камера/микрофон/гео/уведомления)**

4. → затем крупный блок САЙДБАРА (Фазы 0–5, раздел D)

### B1. Загрузки — готовое решение есть
- **Рекомендация: библиотека `electron-dl-manager` (theogravity).** Покрывает: save-as
  диалог, pause/resume/cancel, id на загрузку, restoreDownload, `persistOnAppClose`
  (переживают перезапуск/краш через `will-quit`). Это НЕ писать руками. [источник: GitHub theogravity/electron-dl-manager]
- Базовый слой без библиотеки — `session.on('will-download')` + `DownloadItem`
  (setSavePath/pause/resume/cancel/getReceivedBytes/'updated'/'done'). ~30 строк, но
  тогда restore/persist на себе. [источник: electronjs.org DownloadItem docs]
- ⚠️ Electron `DownloadItem` НЕ даёт явной ловли ошибок загрузок — обрабатывать провалы
  отдельно (библиотека частично обходит). [источник: theogravity README]
- ⚠️ Resume работает ТОЛЬКО если сервер поддерживает range-запросы + отдаёт
  `Last-Modified`/`ETag`. Иначе resume() начнёт с нуля. Ограничение протокола, не лечится.
  [источник: electronjs.org DownloadItem docs]
- Поведение (из спеки 3.7): папка по умолчанию, «спрашивать каждый раз», действия после —
  открыть файл / показать в папке / повторить / отмена.
- ⚠️ Инвариант: загрузки НЕ писать в состояние вкладок/автосейв сессии — отдельное
  хранилище. Изолированный блок, фундамент не трогает.

### B2. Разрешения — готовой библиотеки НЕТ и не нужна (нативный API)
- API: `session.setPermissionRequestHandler` + `session.setPermissionCheckHandler`.
  [источник: electronjs.org session docs]
- ⚠️ Нужны ОБА хендлера. Только request недостаточно — web API сначала делают check;
  без check-хендлера поведение неконсистентно. [источник: electronjs.org session docs]
- ⚠️ БЕЗОПАСНОСТЬ, не только UX: если хендлер не поставить — сессия разрешает ВСЁ, камеру/
  микрофон можно включить молча БЕЗ уведомления (Electron индикатор не показывает, в
  отличие от обычных браузеров). Для приватного браузера критично. [источник: doyensec/electronegativity]
- ⚠️ Гранулярность — решить ДО кода: хранить решения по **origin** (`requestingOrigin`),
  НЕ по вкладке. Хендлер ставится на `session.fromPartition(...)`. Поскольку partition'ы
  разведены (обычные/закреплённые/инкогнито-позже) — вешать хендлер на каждую релевантную
  сессию; у инкогнито своя partition → свои (пустые) решения → разрешение из обычной
  вкладки НЕ течёт в инкогнито. [источник: electronjs.org session docs]
- ⚠️ Инвариант: не ломает split (разрешение по origin активной панели) и автосейв.

## C. ИНВАРИАНТЫ НА ВЕСЬ БЛОК САЙДБАРА (сквозные, проверять на каждом шаге)

- ⚠️ **ЕДИНЫЙ ИСТОЧНИК ИСТИНЫ для порядка вкладок**: один и тот же порядок для отрисовки,

  Ctrl+Tab, автосейв/восстановление после краша.
- Хоткеи — `input.code`. Верификация — автор в окне (drag/split-в-строке = нативщина/
  визуалка, автотесты бесполезны).
- После КАЖДОЙ фазы браузер в рабочем состоянии — можно остановиться.

## D. БЛОК САЙДБАРА — ФАЗЫ 0–5

### Почему такой порядок (НЕ нарушать)
За сайдбар хотят сесть: drag-reorder, split-в-строке (Arc), drag-to-split, AI-группы.
Все требуют, чтобы сайдбар был ДЕРЕВОМ, не плоским списком. Делать их по очереди на
плоской модели = переписать сериализацию автосейва 3–4 раза с риском миграции каждый раз.
⚠️ Фундамент (иерархия) закладывается ОДИН раз в Фазе 0, ДО любого нового UI.

---

### ФАЗА 0 — Фундамент данных. Иерархическая модель. БЕЗ нового UI.
Цель: перевести сайдбар с плоского списка на дерево узлов, СОХРАНИВ поведение полностью
(снаружи ничего не меняется — чистый рефактор под будущее).

- Узел сайдбара трёх типов: **одиночная вкладка / split-пара / группа-контейнер**.
  Сейчас реализуется только «одиночная», но структура сразу умеет в три типа.
- Порядок = порядок УЗЛОВ (дерево), не плоский список вкладок.
- ⚠️ **МИГРАЦИЯ АВТОСЕЙВА** — новая схема сессии. Старые сессии (плоский список) должны
  открыться без падения → написать миграцию. Без неё текущая сессия после обновления не
  восстановится. САМЫЙ ВЫСОКИЙ РИСК ПОТЕРИ ДАННЫХ в блоке.
- ⚠️ Перед первым запуском новой схемы — РУЧНАЯ копия файла сессии (на случай если
  миграция съест данные).
- ⚠️ Заложить: закреплённые рендерятся отдельным типом отображения (сетка иконок —
  см. F), НЕ как узлы общего дерева. Чтобы Фаза 5 не упёрлась в общую отрисовку.
- Чекпоинт Ф0: поведение ИДЕНТИЧНО текущему, внутри уже дерево. Любое отличие → стоп.

### ФАЗА 1 — Drag-reorder одиночных вкладок
- **НЕ писать drag руками. Библиотека `dnd-kit`** (core + sortable + modifiers).
  Стандарт 2025/26, 10kb ядро, DragOverlay через ПОРТАЛ (ghost следует за курсором, не
  трогая DOM). [источник: docs.dndkit.com; brightcoding deep dive; puckeditor top-5]
- ⚠️ Drag ВНУТРИ окна = обычный DOM, нативных модулей НЕ нужно. Нативщина только для
  перетаскивания файлов НАРУЖУ — не наш кейс. [источник: fileside.app; electronjs native-file-drag-drop]
- ⚠️ dnd-kit сортирует в пределах ОДНОГО уровня. Перемещение между уровнями дерева
  (вкладка↔группа) — дописывать РУКАМИ поверх (логика «куда упало в дереве»). Несколько
  источников называют это «troublesome». Это ровно arrayMove-на-дереве из Фазы 0.
  [источник: dev.to/fupeng_wang react-dnd-kit tree; medium @wangfupeng1988]
- DragOverlay через портал — переиспользовать паттерн портала из фикса дропдауна омнибокса
  (один подход к оверлеям на проект).
- ⚠️ Изменённый порядок → в ЕДИНЫЙ ИСТОЧНИК ИСТИНЫ. Проверить: перетащил → перезапуск →
  порядок сохранился, не прыгнул.
- Автосейв на DROP (debounce), не на каждый пиксель.
- Пересечения ДО кода: закреплённые (запретить дроп обычной в их зону, ИЛИ это жест
  «закрепить перетаскиванием» — ВЫБРАТЬ); split-вкладка при drag; спящую НЕ будить.

### ФАЗА 2 — Split в сайдбаре: вид Arc + drag-to-split + свёрнутое состояние
- Отрисовка split-ПАРЫ на одной строке (как Arc) — узел «split-пара» из Ф0 получает визуал.
- Drag-to-split: дроп вкладки НА другую (не между) → split-пара. ⚠️ Разделить зоны дропа:
  между узлами = reorder; поверх узла = split.
- ⚠️ Drag-to-split и существующая кнопка ⊟ ведут в ОДНО состояние split (Вариант Г) —
  переиспользовать, не плодить вторую реализацию.
- **Arc-паттерн (образец, мы не изобретаем):** split = drag вкладки в центр контента или
  на левый/правый край другой вкладки; split сам становится вкладкой в сайдбаре (= Вариант Г).
  [источник: resources.arc.net split-view; arcanesciencelab; blog.warrenweb]
- ⚠️ **Навигационные кнопки (назад/вперёд/обновить) привязать к АКТИВНОЙ ПАНЕЛИ**, не
  только адресную строку. Иначе Arc-баг (как у Vivaldi): жмёшь refresh — обновляется не та
  панель. Arc опускает кнопки на уровень панели именно поэтому. [источник: xda-developers arc hands-on]
- ⚠️ Ограничить ЧИСЛО панелей в split. Arc разрешает много → «тонкие колонки», контент
  обрезается. Задать разумный максимум. [источник: xda-developers; arcanesciencelab]
- Split в свёрнутом сайдбаре: УТОЧНИТЬ у автора — только отображение факта split (две
  иконки/значок) или ещё и управление из свёрнутого. Первое — мелочь, второе — UX-задача.

### ФАЗА 3 — Группы как механика. БЕЗ AI.
- Создать группу, добавить/убрать вкладки, имя, цвет, свернуть/развернуть — РУКАМИ.
- ⚠️ Группы переживают автосейв и перезапуск (узел «группа-контейнер» из Ф0 получает данные).
- Пересечения: закреплённые в группы НЕ попадают (явно прописать); свёрнутая группа →
  усыплять вкладки? (решить); нумерация/Ctrl+Tab учитывают группы в визуальном порядке;
  вкладка из группы в split — поведение.
- Чекпоинт Ф3: группы работают руками, надёжны. **Сайдбар функционально полный без AI.**

### ФАЗА 4 — Первый AI: «Навести порядок». Поверх готовых групп.
AI последний — садится на надёжную механику групп. Иначе не отличить баг кластеризации
от бага сериализации.

- Рантайм: **transformers.js (ONNX)**, модель **`Xenova/all-MiniLM-L6-v2`** (384-мерные
  векторы, ~2M загрузок/мес, ONNX-веса есть), квантизация **`dtype: 'q8'`**.
  [источник: huggingface.co/Xenova/all-MiniLM-L6-v2; dev.to datastax; promptfoo]
- ⚠️ Инференс в WORKER (обязательно — на main морозит UI, прямо подтверждено).
  [источник: sitepoint optimizing transformers.js]
- ⚠️ Первая загрузка модели 8–15 сек + 150–300 МБ пик памяти → ленивая загрузка с
  индикатором, кэш на диск. [источник: sitepoint optimizing transformers.js]
- Кнопка «Навести порядок» — появляется при **>10 незакреплённых активных** вкладок.
- ⚠️ Сигнал для кластеризации = **заголовок + домен** вкладки (короткая строка). НЕ текст
  страницы: лимит модели 256 токенов, качество падает после 128. Title+URL влезает с
  запасом. [источник: dev.to datastax — лимит MiniLM]
- ⚠️ Кластеризация — **порог по косинусной близости (агломерация), НЕ k-means**. Число
  кластеров k заранее НЕИЗВЕСТНО — это главная проблема кластеризации коротких текстов в
  литературе. Для 10–30 вкладок порог проще и предсказуемее, чем угаданный k.
  [источник: arxiv 2511.19350; arxiv 2102.00541 — проблема выбора k]
- Именование групп: ключевые слова из заголовков кластера (надёжный базовый путь) +
  опционально Gemma для красивого имени С ФОЛБЭКОМ на ключевые слова, если выдала мусор.
  Никогда не падает целиком.
- ⚠️ **AI ТОЛЬКО ПРЕДЛАГАЕТ:** кнопка → расчёт → ПРЕВЬЮ групп → пользователь правит/
  принимает/отменяет → ТОЛЬКО после «Применить» TabManager перестраивает. Никогда
  «нажал и само переставило».
- ⚠️ **ОБРАТИМОСТЬ:** сохранить предыдущий порядок до перестройки, дать откат
  (Ctrl+Z / «вернуть как было»). Иначе потеря ручной организации.

### ФАЗА 5 — Визуальный финал сайдбара
- Парящий элемент в стиле macOS (НЕ «android-шторка»), крупнее, читаемее.
- Группы / split-пары / AI-метки / «спит» отрисованы по МАКЕТУ (см. F). Убрать лишние
  элементы.
- Ложится на готовую структуру Ф0–4 как на таргет → не «дизайн с нуля», а «привести к
  макету» → риск ниже.
- ⚠️ Делается ОДИН раз в конце. Красить по ходу = переделывать на каждом структурном
  изменении.
- **Макет сохранить в проект** (папка дизайн-референсов / приложить к BACKLOG) — чтобы к
  Ф5 был под рукой.
