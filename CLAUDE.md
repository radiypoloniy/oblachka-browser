# CLAUDE.md — правила работы над Oblako Browser

Этот файл читается автоматически. Соблюдай его в каждой задаче.

## Что это за проект

Oblako — приватный браузер на Electron (Chromium + Node), Windows x64, со
встроенным VPN и AI. Ядро (окно, вкладки, омнибокс, split, группы, закреп,
усыпление, автосейв сессии), сантехника (адблок, история, загрузки, разрешения
сайтов, пароли/vault) и AI (локальный инференс Qwen через `node-llama-cpp` —
перевод/пересказ/объяснение выделения, перевод страниц, AI-группировка
вкладок, боковая AI-панель с чатом; плюс облачные интеграции — AI-хаб на
новой вкладке с веб-поиском через SearXNG и фактчек через Gemini) — уже
реализованы. VPN — Xray-core дочерним процессом (импорт подписки, генерация
конфига, `session.setProxy`, fail-closed kill switch), поповер «Защита» в
тулбаре объединяет VPN и адблок (см. `src/components/Toolbar.tsx`). Не
позиционируем браузер как «только локальный ИИ» — часть AI-функций облачная,
см. ниже. Актуальный список готового/недостающего — в README.md и в разделе
«Дорожная карта» ниже.

Стек: **Electron 40 + TypeScript (strict) + Vite + React 18**. Иконки — lucide-react.
UI построен на дизайн-системе Oblako (Liquid Glass) через CSS-токены. AI-инференс —
`node-llama-cpp` (локальная LLM Qwen) + `@mozilla/readability` (извлечение текста
страницы). Эмбеддинги/векторный поиск (`@huggingface/transformers`) испытывались
и были удалены из проекта целиком — тупиковый подход на этом корпусе, не баг (см.
`TabOrganizer.ts` и `HistorySearch.ts` ниже). Перевод страниц — движок Bergamot
(WASM/CPU, `@browsermt/bergamot-translator`, свой `worker_thread`) с фолбэком на
Qwen. История — `better-sqlite3` (нативный модуль, требует пересборки под
Electron ABI, см. `postinstall`). Артефакты «Студии» блокнота рисуют
детерминированные либы в renderer: майндкарты — `markmap-lib` + `markmap-view`
(SVG), инфографика — своя вёрстка карточек в `studioViews.tsx` (движок
`@antv/infographic` убран: его шаблоны с фиксированной шириной полей ломали
раскладку, и промптом это не лечилось); модель
отдаёт только структуру/текст (см. «Блокнот» ниже).

## Команды

```bash
npm run dev                          # Vite (5173) + Electron dev-режим одновременно
npm run build                        # vite build + tsc -p electron/tsconfig.json (прод-сборка)
npm start                            # запуск собранного прод-приложения (dist-electron)
npm run dist                         # NSIS-установщик в release/ (без публикации)
npm run release                      # то же + выкладка релиза на GitHub (нужен GH_TOKEN)
npm run make-icon                    # build/icon.png из build/logo-source.png
npm run download-fonts               # woff2-субсеты Golos Text + JetBrains Mono в src/assets/fonts
npm run download-flags               # SVG-флаги стран для списка VPN-серверов (src/public/flags)
npm run download-browser-logos       # логотипы браузеров для экрана переноса данных (src/public/browsers)
npm run download-crypto-icons        # значки монет для виджета «Крипта» (src/public/crypto)
npm run download-filters             # (легаси) EasyList в resources/ — текущий адблок их НЕ читает
npm run download-xray                # бинарник Xray-core для VPN (electron/VpnProcess.ts)
npm run download-translation-models  # пары en<->X для Bergamot из реестра Mozilla Remote Settings
npm run bergamot-smoke               # ручная проверка перевода страниц без UI (см. README)
npm run bookmarks-schema-check       # прогон миграции базы закладок и API папок на временной базе
npm run measure-model                # замер требований GGUF-модели (VRAM/RAM) до скачивания
npm run ai-bench                     # батарея замеров AI-функций на установленной модели
npm run ai-bench -- --model 4b --repeat 3   # то же на другой модели, три повтора на случай
```

Локальная LLM (GGUF, Qwen) скачивается из UI (реестр/каталог моделей —
`electron/ModelDownloader.ts` + `electron/ModelCatalog.ts` + `electron/ModelRegistry.ts` +
`electron/HardwareInfo.ts` (замер VRAM/RAM) + `src/components/ModelsSection.tsx`), отдельного
npm-скрипта для загрузки самой модели нет.

Проверка типов ОБОИХ таргетов (обязательна после изменений, см. «Ритм работы»):

```bash
npx tsc -p tsconfig.json --noEmit         # renderer (src/)
npx tsc -p electron/tsconfig.json          # main-процесс (electron/)
```

Автотестов и линтера в проекте нет. Есть ручные диагностические скрипты в
`scripts/` (`smoke-test.mjs` — запускает прод-сборку через CDP и делает
скриншот в `scripts/shots/`; `check-dom.mjs`, `diag-hub-shadow.mjs` — точечная
диагностика вёрстки). Изолированные AI-стенды запускаются флагами окружения
поверх `npm start`: `OBLAKO_GPU_TEST=1`, `OBLAKO_LLAMA_TEST=1`,
`OBLAKO_TRANSLATE_TEST=1` — открывают отдельное тестовое окно ВМЕСТО боевого
браузера (см. `electron/main.ts`).

## Архитектура — НЕ нарушать

Главный принцип: **UI браузера и веб-страницы — два разных слоя.**

- `electron/main.ts` — главный процесс: создаёт окно и chrome-`WebContentsView`,
  регистрирует весь IPC (`registerIpc`), восстанавливает сессию, подключает
  остальные менеджеры к `session.defaultSession`.
- `electron/TabManager.ts` — ВСЯ логика вкладок: владеет `WebContentsView`
  каждой страницы, показывает/прячет, позиционирует в «дырку» под контент,
  парсит омнибокс, политика `window.open`, split view, группы, закреп,
  усыпление, drag-and-drop порядок. **Логика живёт здесь, не в компонентах.**
  ⚠️ **Усыпление идёт по ДВУМ критериям, и второй важнее первого.** Часы (2 ч обычной вкладке,
  8 ч закреплённой) — спокойный путь. Второй повод — давление памяти: суммарный Working Set
  приложения (`app.getAppMetrics()`) перевалил бюджет. Без него не выгружалось практически
  ничего: замер против Яндекс.Браузера на одинаковых 20 сайтах дал 5688 МБ против 4428 МБ
  (+1,25 ГБ), при почти равных Private Bytes (2955 против 2795). **Равные Private при разном
  Working Set — это не «мы жирнее», это «мы не отдаём память системе».** После правки тот же
  профиль сходится к 3709 МБ, то есть НИЖЕ Яндекса, и механизм останавливается сам, уйдя под
  бюджет (проверено 13-минутным прогоном; закреплённые не тронуты ни разу).
  • Бюджет — ДОЛЯ памяти машины (20%) с границами 1 и 4 ГБ. Обе несущие: без нижней на слабой
    машине это вечное усыпление, без верхней на 64-гигабайтной станции не сработает никогда.
  • Порог простоя действует и под давлением (5 мин обычной, 30 мин закреплённой), закреплённые
    стоят в очереди последними: вернуться через минуту и увидеть перезагрузку хуже, чем лишние
    сотни мегабайт.
  • За проход усыпляем максимум три. Память освобождается не мгновенно, и повторный замер сразу
    после закрытия вью показал бы, что легче не стало, — усыпили бы всё подряд.
  • Проверка «можно ли усыпить» — ОДИН метод на оба критерия (`#canSleepNow`). Две копии защит
    (звук, заполненные формы, split, инкогнито) однажды разъедутся, а узнает об этом человек,
    у которого выгрузило форму на полуслове.
  ⚠️ Известная неточность: таймер свой у КАЖДОГО окна, а бюджет общий на приложение, поэтому в
  одну минуту несколько окон могут усыпить по три штуки каждое, прежде чем память просядет.
  Само себя исправляет следующей проверкой; городить общий на приложение планировщик ради
  этого пока не стали.
  Инкогнито-вкладки: флаг `incognito` + партиция `INCOGNITO_PARTITION` (in-memory
  сессия, см. `shared/ipc.ts`) — не пишут историю, исключены из автосейва, не
  усыпляются; вход — кнопка-маска/Ctrl+Shift+N/ПКМ.
  ⚠️ **Приватность НАСЛЕДУЕТСЯ: всё, что рождается от приватной страницы, тоже приватно.**
  Флаг `incognito` — четвёртый аргумент `createTab`, и он по умолчанию `false`, поэтому любой
  забытый вызов молча создавал обычную вкладку с куками основного профиля, записью в историю и
  попаданием в автосейв. Так и было в шести местах сразу: `setWindowOpenHandler`, «Открыть
  ссылку в новой вкладке», «в split», «Открыть картинку в новой вкладке» и оба пункта поиска по
  выделенному (последнее хуже всего — наружу уходил текст, выделенный на приватной странице).
  Пункт «Открыть ссылку в инкогнито» к этому не относится: он ПОДНИМАЕТ приватность из обычной
  вкладки, это другое действие. ⚠️ Проверять такое только замером, и признак сессии — КУКИ:
  у приватной свой in-memory кувшин, поэтому «какую куку прислала открытая вкладка» отвечает на
  вопрос «в какой она сессии» однозначно, а по внешнему виду вкладки этого не видно вовсе.
  Привязка адблока/загрузок/
  разрешений/прокси-VPN к инкогнито-сессии — в `main.ts` (адблок в доп. сессии —
  ТОЛЬКО сетевая блокировка: `enableBlockingInSession` нельзя звать дважды);
  очистка in-memory данных при закрытии последней приватной вкладки —
  `TabManager.takeIncognitoClearIfDone`.
- Видео: полноэкранный режим и «кадр следует за вами» — в `TabManager.ts` плюс
  `electron/videoPip.ts`. ⚠️ Полный экран: Chromium растягивает видео по СВОЕЙ
  `WebContentsView`, а она занимает лишь дырку под контент, — поэтому на
  `enter-html-full-screen` вью раздвигается на всё окно (и окно уходит в fullscreen),
  скругление снимается, а присланные рендерером bounds на эту вкладку не действуют, иначе
  первый же `ResizeObserver` вернул бы кадр в дырку. ⚠️ Picture-in-Picture: замерено, что
  Electron 40 поддерживает его целиком и окошко ПЕРЕЖИВАЕТ переключение вкладки (видео
  играет, хотя `document.hidden` истинно) — своё плавающее окно не понадобилось. Запрос
  требует жеста человека, поэтому скрипт идёт через `executeJavaScript(code, true)`; без
  второго аргумента он отклоняется. Уводим только играющее видео заметного размера и
  уважаем `disablePictureInPicture`.
- `electron/WindowRegistry.ts` — реестр окон (в работе, многооконность по срезам).
  Контекст окна — окно, слой хрома, свой `TabManager`, роль (`'main'` — полное,
  владеет сессией и службами-одиночками; `'light'` — только вкладки, омнибокс,
  поиск по странице). ⚠️ **Три разных адресата, не путать:**
  `contextFromSender(e.sender)` — окно, приславшее вызов (весь IPC вкладок, диалоги,
  меню, ответные пуши вроде стрима чата и прогресса графа: адресат запоминается в
  момент запроса, а не ищется к моменту ответа); `broadcastToChrome(...)` — общее
  состояние приложения (закладки, пароли, автозаполнение, VPN, адблок, загрузки,
  модели, обновления): файл на диске один, а копия списка у каждого окна своя;
  `mainWin/mainChromeView/mainTabs/mainSess` в `main.ts` — ЗАПАСНОЙ путь для
  отправителей вне реестра (ранние сообщения при старте, изолированные тестовые
  окна) и адрес финального сохранения сессии, а НЕ «текущее окно».
  `createWindow(role)` делится на три части: `wireSharedSessions()` — один раз на
  приложение (орфография, перехват загрузок, разрешения, инкогнито-сессия; второй
  `downloads.attach` навесил бы второй `will-download`); своё у каждого окна — окно,
  хром, вкладки, хоткеи; только у полного — сессия и службы-одиночки (AI-панель,
  быстрый поиск Ctrl+E, перевод страниц, группировка, поповеры паролей и
  автозаполнения). ⚠️ Закрытие лёгкого окна НЕ трогает `session.json` и не убивает
  `xray.exe` — это про выход из приложения, а не про окно.
  Оверлеи — «свои у каждого окна»: `FindBarManager`, `SuggestDropdownManager`,
  `PasswordPopoverManager`, `AutofillPopoverManager` (состояние в карте по id окна,
  окно ищется по вью-отправителю, потому что `BrowserWindow.fromWebContents` для
  дочерней вью отдаёт null). `PasswordAutofillManager`/`AutofillOrchestrator`
  менеджер вкладок не хранят вовсе — каждая точка входа получает окно, вкладки
  берутся из реестра по нему (иначе форма входа в одном окне искала бы активную
  вкладку в другом). Ещё НЕ развязаны и потому принадлежат полному окну: AI-панель,
  быстрый поиск (Ctrl+E), перевод страниц, AI-группировка, поповер VPN, поповер
  перевода — в лёгком окне их входы спрятаны (см. `isLightWindow` в `App.tsx`).
  Вход: Ctrl+N и канал `WINDOW_OPEN` (создаётся всегда лёгкое окно). Роль доезжает
  в renderer через `WINDOW_GET_ROLE`, тип `WindowRole` — в `shared/ipc.ts`.
  Перенос вкладки в новое окно — ПКМ «Открыть в новом окне» и вытаскивание из
  сайдбара за край окна (`TabManager.detachTabForMove`/`adoptTab`). ЖИВАЯ вкладка
  уезжает своей `WebContentsView`, а не открывается по адресу заново: у страницы
  остаются история «назад», прокрутка и введённое в форму. СПЯЩАЯ переносится
  описанием (url/заголовок/иконка) — вью у неё ещё нет, терять нечего; без этого
  случая пункт меню гас бы почти всегда, ведь после перезапуска спящие почти все.
  Закреплённая переносится и в новом окне становится обычной (закреп — место в
  полосе конкретного окна, а не свойство страницы). Не переносятся только хаб,
  псевдо-вкладки и участник split (увёл бы за собой половину пары).
  ⚠️ Слушатели прежнего менеджера снять нечем (`removeAllListeners` снёс бы и
  чужие — видео, PiP, индексация), поэтому каждый обработчик в `wirePageEvents`
  начинается с проверки `mine()`: ушедшую вкладку обслуживает уже новый владелец.
  ⚠️ Факт «вытащили за окно» определяет MAIN (`WINDOW_POINTER_OUTSIDE`,
  `screen.getCursorScreenPoint()`), а не рендерер: как только курсор уходит за край
  окна, движения рендереру не доставляются, и его координаты упираются в границу.
  Синтетическими событиями CDP это не проверяется — они доставляются с любыми, в
  том числе внешними, координатами. Отпускание над ДРУГИМ окном Oblako сейчас тоже
  считается «наружу» и создаёт третье окно.
  ⚠️ **Зоны дропа поверх страницы** — `electron/DropZoneManager.ts` + `src/dropzones.tsx`
  (своя прозрачная вью на время перетаскивания, свой preload, свой entry в
  `vite.config.ts`). Края контента по 35% ширины — разделить экран, середина или
  вообще вне окна — новое окно; подсвечивается зона под курсором, с подписью.
  Зачем зоны: у окна во весь экран «снаружи» нет вовсе, и жест не может зависеть от
  границы окна. Chrome обходится без них (полоса вкладок горизонтальная и тонкая:
  «вне полосы» = «новое окно»), но у нас полоса вертикальная и вне её — страница,
  уже занятая разделением экрана; браузеры с вертикальными вкладками и сплитом
  (Zen, Arc, Vivaldi) разводят это ровно зонами.
  ⚠️ **Два закона, из-за которых это не могло жить в чроме** (оба проверены живьём,
  и оба НЕ ловятся синтетическими событиями CDP — те доставляются прямо в рендерер
  и с любыми координатами): нативная вью страницы лежит ПОВЕРХ React-слоя, поэтому
  нарисованная в `App.tsx` подсказка невидима; и чром перестаёт получать
  `pointermove`, как только указатель уходит на страницу, — он видит лишь последнюю
  позицию у кромки контента, то есть «край», то есть всегда разделение экрана.
  Поэтому зону считает MAIN по `screen.getCursorScreenPoint()` (опрос 30 мс живёт
  ровно во время драга), а сайдбар только спрашивает её в конце. На вью висит тот
  же **страж фокуса**, что у выпадашки подсказок: без него вью забирает фокус
  (electron/electron#42922) и обрывает само перетаскивание.
  Подпись — не украшение: у одного дропа два исхода, и человек должен видеть,
  какой получит, до отпускания.
  ⚠️ **Возврат вкладки в открытое окно** (обратный жест к выносу — вытащить окно легко и
  легко случайно, а вернуть было нечем): отпускание над ДРУГИМ окном Oblako теперь не
  создаёт третье окно, а отдаёт вкладку тому окну — зона `'adopt'`, подсветка рисуется в
  окне-ПРИЁМНИКЕ (человек смотрит туда, куда тащит), решение везёт `TabDropResult`
  (зона + id окна). Состояние драга живёт одним объектом на приложение, а не в записи
  окна: в жесте участвуют ДВА окна. Порядка окон по глубине Electron не отдаёт — своё
  окно проверяется первым, среди чужих берётся первое подходящее.
  Ещё два входа для того же: пункт ПКМ «Вернуть в главное окно» / подменю «Перенести в
  окно» и Ctrl+Shift+M. Лёгкое окно, из которого унесли последнюю страницу, закрывается
  само (`closeIfEmptyLight`) — полное не трогаем никогда, оно владеет сессией.
  ⚠️ **Порядок в списке применяется СИНХРОННО в `onDragEnd`** (`planReorder` в
  `Sidebar.tsx`), а команда в main — уже после ответа о зоне; при не-сайдбарном исходе
  порядок откатывается (`revertLocalOrder`). Раньше ждали и порядок тоже, и вкладка на
  глазах возвращалась откуда взяли: dnd-kit запускает анимацию приземления в тот же миг,

- `electron/BookmarkManager.ts` — закладки на своём `bookmarks.sqlite`

  ⚠️ Три вещи в схеме, каждая из которых иначе ломается тихо:
  • **`kind`, а не «пустой url»** — url объявлен NOT NULL, пустая строка это
    обычное значение, и две папки немедленно столкнулись бы в индексе
    уникальности адресов; вторая молча не создалась бы.
  • **`ON DELETE CASCADE` у `parent_id`** — без него при `foreign_keys = ON`
    удаление папки с содержимым не «оставляет сирот», а ПАДАЕТ с ошибкой. В
    SQLite ограничение через `ALTER` не меняется, отсюда перестройка таблицы.
  • **оба индекса уникальности частичные и оба с `kind = 'link'`** — в корне
    обычный `UNIQUE(parent_id, url)` не сработал бы вовсе (SQLite считает каждый
    NULL уникальным даже в составном индексе), а без условия по `kind` две папки
    в одном родителе считались бы дубликатом друг друга.

  ветка просто исчезает из дерева (обход от корня в неё не заходит).

  ⚠️ **Основной способ создать правило — ФОРМА** (`RulesSection.tsx`: два ряда вариантов, поле
  сайта с подсказками из своей истории, имя группы), а фраза — вторая дорожка. Разбор фразы
  моделью тут удобство, а не механизм: каталог закрыт и мал, правило это форма из четырёх полей,
  и модель на такой задаче лишь теряет точность (см. отсеивающий вопрос в начале раздела
  «Программа»). Плюс модель опциональна — пока единственной дверью была фраза, у человека без
  скачанной модели раздел не работал вовсе. Подсказки сайтов берутся из истории (`searchHistory`),

  ⚠️ Разбор фразы — `electron/RuleParser.ts`, ответ ПОМЕЧЕННЫМИ СТРОКАМИ (`TRIGGER:`/`DOMAIN:`/
  `ACTION:`/`GROUP:`), не JSON: каждое поле разбирается своей меткой и не зависит от соседних.
  ⚠️ **Триггер спрашивается ОТДЕЛЬНЫМ коротким прогоном**, а не пятым полем общего ответа: это
  единственное место разбора, где 9B «плавала» — на одной и той же фразе ответ менялся между
  прогонами. Вынесли решение в свой прогон — стало 7 из 8 при нуле шатких случаев (было 5 из 8 и
  два шатких). Почему так работает — в разборе недетерминированности (раздел «Программа» ниже).
  Ответ общего промпта остаётся запасным: если короткий прогон не удался, лучше догадка, чем отказ.
  Три урока замера на живой 9B (было 5 из 8 → стало 7 из 8):
  • **Пример настоящего домена в промпте работает ответом по умолчанию.** Пока в инструкции
    стояло «("хабр", "озон") → habr.com, ozon.ru», модель отвечала `habr.com` даже на фразу с
    явно названным `vtb.ru` и на фразу вообще без сайта. Реальных доменов в промпте нет.
  • **Триггеры надо ПРОТИВОПОСТАВИТЬ** («страница НА сайте» против «страница НЕ на сайте») и
    отдельно разобрать русские обороты: «ссылки с сайта»/«переходы с сайта» — это `link-from`,
    «на сайте»/«вкладки с сайта» — `site`. Без этого «ссылки с хабра» уверенно уходили в `site`.
  • **Явно названный домен проверяется КОДОМ, а не доверием к модели** (`domainMismatch`): если
    в фразе есть домен, ответ обязан совпасть с ним. Это самая опасная ошибка разбора — карточка
    выглядит правильной, а домен в ней чужой, глазами не поймать.
  ⚠️ **Действию «группа» имя обязательно, но не обязательно ОТ МОДЕЛИ.** Человек говорит «в
  отдельную группу», не называя её, — модель честно ставит прочерк, и правило отбраковывалось
  целиком: на образцово разобранной фразе («ссылки с habr.com открывай в отдельной группе»
  модель отвечает верно во всех полях) человек видел «не понял фразу». Теперь имя берётся от
  домена (`groupNameFromDomain`: habr.com → «Habr») и правится в карточке.
  Остаточная ошибка (осознанная): на фразу вне каталога («удаляй историю каждый вечер») модель
  вместо `TRIGGER: none` придумывает правдоподобное правило. Ловит его человек — карточка
  подтверждения показывает правило словами, и «ссылки с example.com — не блокировать рекламу»
  на просьбу про историю не подтвердит никто. Это и есть роль карточки, а не косметика.

  столько, сколько влезает в СВОБОДНУЮ видеопамять, — то есть **чем меньше модель, тем больше ей

  мучительно медленнее 9B», и это оказалось правдой ровно по этой причине. Потолок 16384 взят от

  использованием.

  экраном, и с содержимым, а выбрать себе градиент из галереи (15 пресетов, `WALLPAPER_PRESETS`)
  человек может одним кликом. Отсюда же светлый режим вкладки: палитра текста и «стекла» живёт
  в CSS-переменных `--nt-*` и переключается по `isLightBackground` — на белом фоне прежний
  белый текст был бы просто не виден.
- **Рабочий стол новой вкладки** (springboard в духе iPad) — `src/components/desktop/`:
  `DesktopScreen.tsx` (фон, поиск, отрисовка), `widgets.tsx` (виджеты), `SiteIcon.tsx` (иконки
  сайтов), модель и движок раскладки — `src/newtab/desktop.ts`. Заменил прежнюю минималистичную
  вкладку (`NewTab.tsx` удалён).
  ⚠️ **ЧИСЛО КОЛОНОК ПОСТОЯННО** (живёт в самой раскладке — это система координат плиток, а не
  украшение; меняется вместе с размером плиток, см. `SCALE_PRESETS`: мелкий 8×110, средний 6×120,
  крупный 5×140 — одна ручка на два числа, порознь они бессмысленны). Значения не выдуманы: пока
  колонки считались от ширины, клетка жила в вилке 110…132 (на области 1320 px — 10 колонок по
  119, на 1100 — 9 по 110, на 900 — 7 по 117), и ниже 110 стол не опускался никогда. Сама
  заморозка сделала стол крупнее (6 колонок вместо 9–10 при клетке в потолок), поэтому «мелкий»
  возвращает ровно прежние 244 px на плитку 2×2, а «крупный» оставляет то, что вышло после
  заморозки. ⚠️ Потолок ЗАЗОРА (`GAP_MAX = 24`) — тоже про размер, а не про воздух: зазор входит
  внутрь многоклеточной плитки, и при 40 px плитка 2×2 пухла с 264 до 280. При сжатии окна
  меняется РАЗМЕР КЛЕТКИ, а не расклад: сетка одна и та же от 520 до 2560 px, как springboard на
  iPad (6×5 и на 11", и на 13"). Замерено: при 1400/1000/760 px раскладка совпадает до элемента,
  отличается только клетка (132/97/90). Клетка упирается в `CELL_MAX`, дальше растёт ЗАЗОР до
  `GAP_MAX` — иначе на широком окне шесть колонок собирались бы в тесный островок посреди пустоты.
  ⚠️ Раньше колонки считались от ширины (4…10), и из этого следовало ВСЁ остальное: раз в сетке
  то пять колонок, то девять — координаты хранить нельзя, значит хранится порядок, значит место
  вычисляется заново на каждую ширину, а любое правило пересчёта — выбор из двух зол (жадное
  затыкает дыры, но плитки переезжают сами; последовательное никого не двигает, но оставляет
  дыры). Две жалобы — «при сжатии окна появляются пустоты» и «поставить как нравится нельзя» —
  были одной и той же плавающей сеткой, а не двумя разными задачами.
  ⚠️ **Элементы хранят КООРДИНАТЫ** (`col`/`row` в клетках, формат раскладки v2, `placeItems`).
  Плитка стоит там, куда её положили, дыры между плитками сохраняются — это выбор человека, а не
  побочный эффект укладки, и перенос одной плитки не касается остальных вообще. Прежние укладки
  по порядку (сначала жадная, потом последовательная с заглядыванием на соседа) обе были
  паллиативом: жадная затыкала дыры кем попало («сдвинул одну — переехала другая»),
  последовательная не двигала никого, но дыру закрыть было нечем — элемент всплывал в ближайшую
  свободную клетку выше. `layoutItems` (последовательная) осталась ровно для двух случаев, где
  расставлять приходится ЗА человека: перенос старой раскладки и смена плотности сетки.
  ⚠️ Перетаскивание — В КЛЕТКУ, а не в позицию списка: клетка считается по УГЛУ плитки (плитка
  примагничивается к ближайшей), контур цели показывает исход ДО отпускания, а его отсутствие —
  отказ. Занятая клетка разбирается двумя исходами: ровно один элемент того же размера — обмен
  местами (иначе поменять две иконки было бы нечем, свободной клетки рядом может не быть);
  во всех прочих случаях отказ, потому что раздвигание соседей «как получится» — это ровно то,
  от чего уходили. Гистерезис, порог в треть клетки и база «раскладка без перетаскиваемого»
  исчезли вместе с укладкой по порядку: соседи не двигаются, колебаться нечему.
  ⚠️ В режиме правки снизу добавляется ПУСТАЯ строка — иначе положить плитку ниже последней
  физически некуда, сетка кончалась на последнем элементе.
  ⚠️ **У виджета есть МИНИМАЛЬНЫЙ размер** (`WIDGET_MIN` в `desktop.ts`) — это договор с
  отрисовкой, а не вкус. Тянуть за угол можно было любой виджет до 1×1, и там содержимое
  налезало само на себя: у «Курса ЦБ» заголовок сталкивался с «USD · 30 дней», у «Защиты»
  счётчик уезжал под заголовок, а «заблокировано за сеанс» рвалось на три строки. Адаптацией
  это не лечится — в 97 px нельзя показать число и подписать его. Минимум соблюдают и ручка
  растягивания, и ЧТЕНИЕ раскладки с диска (`clampSize` в `loadDesktop`): у людей уже лежат
  плитки, утянутые до 1×1 руками, и без починки при чтении фикс не дошёл бы до тех, у кого
  проблема и есть.
  ⚠️ На разрешённом минимуме (2×1) «Курс», «Крипта» и «Защита» рисуют ОТДЕЛЬНЫЙ тесный вид, а
  не тот же самый ужатый: одна строка вместо двух, без подписи графика и без спарклайна. Кегль
  считается от реально доступной высоты (`rowFontSize`), а не как «высота минус 60» — прежняя
  формула на низкой плитке уходила в отрицательные числа. ⚠️ И по ШИРИНЕ тоже: по одной высоте
  на плитке 2×2 выходил кегль 26, в который строка «$ 80.07 ▲ 0.76%» не влезала, и процент
  обрезался краем плитки (переносить его нельзя — сломается столбец цифр). Ширина считается в
  единицах кегля: знак ≈1.1 em, цифра ≈0.62 em (моноширинные), плюс фиксированное место под
  процент — он рисуется мелким кеглем и от кегля строки не зависит.
  ⚠️ Переходы у плиток (`transform`/`width`/`height`, 220 мс) ГАСЯТСЯ на кадр, в котором
  изменилась геометрия сетки (`metricsChanged`). Они нужны для правки раскладки — переставили
  плитку, соседи разъехались; но при ресайзе окна клетка меняется каждый кадр, и те же 220 мс
  превращались в отставание: контейнер уже нового размера, а плитки ещё едут к нему — со
  стороны «иконки не поспевают за окном».
  ⚠️ `normalize` (запись фактических координат назад) обязателен после каждой правки: у только
  что добавленного элемента координат ещё нет, их назначает укладчик, и без записи сохранённое
  разошлось бы с увиденным — первая же смена плотности разложила бы стол не так, как он выглядел.
  ⚠️ А ПОЛА у размера клетки нет намеренно, хотя был (`CELL_MIN`): он делал сетку шире
  отведённой области. Дальше шёл замкнутый круг —
  горизонтальная полоса прокрутки съедала высоту → появлялась вертикальная → та отнимала ширину
  → сетка пересчитывалась. Это и было дрожанием виджетов на узком окне (примерно треть монитора):
  не рывок, а колебание между двумя раскладками несколько раз в секунду. Вторая половина
  починки — `scrollbarGutter: 'stable'` у прокрутки в `DesktopScreen.tsx`: пока наличие полосы
  меняет ширину, любая раскладка «от ширины» рискует зациклиться.
  Приложения (калькулятор, конвертер…) переиспользуются из AI-панели: реестр `APPS` и
  `AppIconBadge` экспортированы из `aiApps.tsx`, а иконка на столе открывает панель сразу на
  нужном приложении (канал `AI_PANEL_OPEN_APP` → `openAiPanelApp`). Настройки часов, города
  погоды и валют остались в разделе «Интерфейс» и читаются самими виджетами; тумблеров
  «показывать» там больше нет — состав экрана определяется тем, какие виджеты на нём стоят.
  ⚠️ **Два рода плиток, и это не вкус:** ЦВЕТНАЯ (погода, часы, часто открываемые сайты) —
  носитель со своим настроением, там цвет что-то значит; ПЛИТКА ТЕМЫ (курс, крипта, дела) берёт
  `var(--surface)` и темнеет вместе с интерфейсом и палитрой. Прежний литерал `#FFFFFF` в тёмной
  теме светил на весь стол белым прямоугольником — до открытия тёмной темы этого никто не видел.
  По той же причине тона роста/падения стали токенами (`--tone-green`/`--tone-warm` в `colors.css`
  + светлые ступени в `theme-dark.css`): тёмно-зелёный на тёмной плитке давал контраст около 2:1.
  Часы — циферблат со стрелками по умолчанию (`clock.face`, свой SVG в `widgets.tsx`, как
  спарклайн), цифры остались вторым вариантом; `hour24` осмыслен только у цифр и в настройках
  прячется, `seconds` у циферблата означает секундную стрелку.
- Прежняя новая вкладка (минимал, в духе Bonjourr) — УДАЛЕНА, см. рабочий стол выше (рендерится

  своя `WebContentsView` и свой preload, это не часть `src/App.tsx`.

  обои, локальные приложения, виджеты, веб-слоты; токены — `tokens/apps.css`).
- Анимации. Токены движения уже есть (`tokens/effects.css`: `--ease-standard`/`--ease-out`,
  120/180/260 мс, «quiet and quick, no bounces»). ⚠️ Нативную `WebContentsView` анимировать
  НЕЛЬЗЯ: показ — это `setVisible`, положение — `setBounds`, оба мгновенны, CSS до них не
  дотягивается (тот же закон, что у окон веб-приложений в графе и у выхода из полного экрана).
  Обход для оверлеев — `src/overlayReveal.ts`: вью появляется мгновенно, но её содержимое в
  первый кадр прозрачно и проявляется за 180 мс, поэтому щелчка не видно. Триггер —
  `visibilitychange`, а НЕ монтирование React: вью при скрытии не уничтожается, компонент
  монтируется один раз, а показов сотни (проверено: скрытая вью сообщает `document.hidden`).
  Анимировать только `transform`/`opacity` — они не трогают вёрстку; `backdrop-filter` не
  анимировать никогда, стеклянная система съест кадры.
- `src/styles/tokens/` — токены дизайн-системы. Цвета/радиусы/тени берутся
  отсюда через `var(--...)`, **не хардкодить цвета в компонентах.**
- Тема и палитра. ДВЕ оси, не одна: `data-theme` отвечает на вопрос «светло или темно»
  (`theme-dark.css`), `data-palette` — «какой оттенок нейтрали» (`palettes.css`: уголь=Apple iOS
  по умолчанию, графит=macOS, сланец=Nord, бумага=тёплая). Палитра меняет ЗЕМЛЮ (фон, поверхности,
  разделители, текст) и НЕ трогает акцент — цветовой закон ниже остаётся в силе. У каждой палитры
  есть оба варианта: выбор палитры не должен отменять выбор темы.
  ⚠️ Селекторы палитр писаны парами `:not(...)`: светлый блок отсекает `[data-theme="dark"]`
  (иначе применялся бы в обеих темах и перекрывал тёмный по порядку подключения), тёмный отсекает
  `[data-incognito="true"]` — инкогнито обязано выглядеть одинаково при любой палитре, а его
  селектор слабее пары атрибутов и без гварда проиграл бы.
  Выбор человека живёт в main (`SettingsManager`, `settings.json`, каналы `THEME_GET/SET/CHANGED`),
  а не в localStorage рендерера: тему обязаны знать ВСЕ окна и каждый поповер со своим document.
  Применяет её по-прежнему рендерер у себя (`App.tsx`), в отдельные вью main раздаёт атрибуты сам
  (`chromeThemeJs`) — и ставит их себе ДО первого сообщения от хрома, иначе поповер, открытый
  раньше, вспыхнул бы светлым. Режим «как в системе» читает `nativeTheme.shouldUseDarkColors` и
  слушает `nativeTheme.on('updated')`. ⚠️ `nativeTheme.themeSource` при этом НЕ трогаем: он
  управляет и тем, какой `prefers-color-scheme` видят сами САЙТЫ, а тёмный интерфейс браузера —
  не повод перекрашивать чужие страницы (Chrome разводит это на два разных решения).
  ⚠️ Цвет зоны системных кнопок (`setTitleBarOverlay`) больше не литерал: он читается из живого
  `--app-bg` — теней у этого токена стало восемь, и любой хардкод означал бы полосу чужого цвета.
  Рабочий стол новой вкладки палитре НЕ подчиняется — он красится от своих обоев (`--nt-*`,
  `isLightBackground`), это отдельная ось, см. выше.

Правило: React рисует рамку, main-процесс кладёт WebContentsView в область
контента. Renderer измеряет область (ResizeObserver) и шлёт bounds в main.

## Цветовой закон (строгий, из дизайн-системы)

- Акцент — ОДИН (сейчас `--accent`). Активные состояния, send, выделение, фокус.
- Синий (`--system`) — ТОЛЬКО облако/система. Не для ссылок и декора.
- Зелёный (`--dot-local`, `--dot-vpn`) — функционально: локальная модель / VPN жив.
- Перекраска делается подменой ЗНАЧЕНИЙ токенов в `colors.css`, не имён и не
  компонентов. Функциональные цвета (зелёный=локально, синий=облако) не трогать.
- Палитры (`palettes.css`) — исключение только по ЗЕМЛЕ: фон, поверхности, разделители, текст.
  Акцент и функциональные цвета палитра не переопределяет ни в одной из них.
- **Фиолетового в системе нет вообще** — ни токена, ни литерала. Спека дизайн-системы не
  содержит ни одного фиолетового/розового токена (см. шапку `colors.css`), но сиреневый уже
  дважды просачивался обратно через значки: `--tile-purple`/`--tile-indigo` красили «Интерфейс»
  и «AI» в настройках, тип «картинка» и «код» в загрузках, плюс литерал `#AF52DE` у глифа
  «Цвета» и сиреневая ступень в `--appicon-color`. Убрано; вместо них `--tile-red`,
  `--tile-brown`, `--tile-slate`. Если понадобится ещё один цвет значка — брать из этого
  набора, а не «добавить фиолетовый, он тут подходит».
  ⚠️ Правило распространяется и на СГЕНЕРИРОВАННЫЙ цвет. Подложка под иконку сайта на столе
  выводилась из домена как `hash % 360`, то есть раздавала весь круг вместе с сиреневым
  сектором: `translate.yandex.ru` попадал ровно на 272°, `t.me` — на 282°. Значок сайта при
  этом прозрачный, и весь квадрат светил нашим фиолетовым, хотя у сайта его в логотипе нет.
  Теперь оттенок берётся из фиксированного набора — `src/components/desktop/siteTint.ts`,
  один на `SiteIcon.tsx` и на плитку-фолбэк в `widgets.tsx`.

## Как писать код

- **Чистота и читаемость важнее ранней оптимизации.** Не оптимизируй вслепую.
  Оптимизация — только прицельно там, где измеримо тормозит на живых тестах.
- TypeScript strict. Не глуши ошибки через `any`/`@ts-ignore` без причины и
  комментария, почему иначе нельзя.
- Комментарии — по-русски, объясняют ЗАЧЕМ (намерение, риск), а не ЧТО.
- Не добавляй зависимости без явной нужды. Если добавляешь — скажи зачем.
- Не рефактори то, о чём не просили. Узкая задача = узкая правка.

## Ритм работы — строго

- **Одна фича за заход.** Не браться за две сразу — иначе при поломке не понять,
  что виновато.
- После изменений: собери (`npm run build`) и проверь типы ОБОИХ таргетов
  (`tsc -p tsconfig.json --noEmit` и `tsc -p electron/tsconfig.json`) ДО того,
  как сказать «готово».
- Не ломай то, что уже работает. Если правка задевает рабочую функцию —
  предупреди заранее.

## Кроссплатформенность (прицел на macOS-порт)

Проект сейчас Windows x64, но macOS-версия в планах. Чтобы порт был «дописать
слой», а не «переписать проект», ВЕСЬ платформенно-зависимый код изолируй за
интерфейсами/абстракциями, а не размазывай по проекту:
- **Хранилище секретов** (пароли/vault, ключи Gemini): уже кроссплатформенно —
  `electron/VaultCrypto.ts`/`AiKeyStore.ts` заворачивают через Electron
  `safeStorage` (DPAPI на Windows, Keychain на macOS из коробки), отдельный
  `SecretStore`-интерфейс не потребовался. Остальной код не завязан на
  конкретный механизм шифрования.
- **Запуск VPN/Xray**: абстракция над спавном процесса и настройкой прокси —
  реализации Windows / macOS отдельные.
- **AI-runtime / VRAM-бюджет**: учитывать, что Windows = NVIDIA/CUDA + выделенная
  VRAM, macOS = Apple Silicon/Metal + unified memory. Логика бюджета за
  платформенным интерфейсом.
- **Titlebar/окно**: Windows titleBarOverlay vs macOS trafficLight (кнопки слева).
  Раскладку шапки делать условной по платформе, не хардкодить под Windows.
Правило: если код вызывает ОС-специфичный API — он живёт за интерфейсом с
платформенными реализациями, а не инлайн в общей логике.

## Безопасность данных и стоп-условия

- Автосейв сессии (`electron/SessionManager.ts`) есть и синхронно пишет
  `session.json` в `win.on('close')`, но формат версионирован (сейчас v4) и
  хранит реальные пользовательские данные (открытые вкладки/группы). Ломка
  формата или гонка в моменте сохранения/восстановления = потеря вкладок
  пользователя — трогать этот код особенно осторожно.
- Перед изменениями, которые трогают данные на диске (автосейв, история в
  `better-sqlite3`, профиль, vault, миграция формата) или внешние процессы
  (будущий Xray/VPN) — **предупреди о риске потери данных или сломанного
  билда** и предложи проверить на пустом профиле / сделать коммит.
- Не давай указаний и не пиши код, которые могут привести к откату прогресса,
  потере данных или сломанной сборке, без явного предупреждения.
- ⚠️ **Диагностика идёт на БОЕВОМ профиле.** Скрипты из `scripts/` и разовые
  проверки через CDP запускают собранное приложение, а оно открывает настоящий
  `userData` пользователя — с его историей, закладками, графами и сессией.
  Никогда не начинать проверку с очистки существующих данных: создавать своё и
  удалять ТОЛЬКО созданное. Живой случай: проверки узлов графа начинались со
  строки, снимающей все воркспейсы, и стёрли пользовательские холсты.

## Принцип AI в Oblako — «незаметный ИИ»

⚠️ **Это главный фильтр для любой AI-идеи в проекте, читать до критерия пригодности ниже.**
Oblako не делает ассистента-собеседника и не делает агента, который действует за человека. Мы
делаем **незаметный ИИ, который снимает рутину и предлагает решения**, а нажимает и подтверждает
человек. Три следствия, каждое уже оплачено работой:
- **Предлагать, а не делать.** Правило рождается из фразы, но заводится карточкой подтверждения;
  группировка предлагается кнопкой «Навести порядок» и откатывается одним движением; смысловой
  поиск подсвечивает место на странице, а не пересказывает его своими словами.
- **Не лезть в чувствительные зоны.** Никаких действий от имени человека на чужих сайтах,
  никакой автоматизации переписки и оплат, никаких необратимых действий по догадке модели.
  Каталог правил закрыт и мал именно поэтому. Отдельно см. разбор prompt injection: в агентных
  браузерах (Comet, Atlas) он в принципе не чинится, потому что агент работает с полными правами
  залогиненного человека — мы такой конструкции избегаем by design.
- **Не соревноваться с облаком там, где проиграем.** Написать текст, поспорить, поработать
  «вторым мозгом» человек пойдёт в ChatGPT или Claude, и это нормально: отказываться от них ради
  приватности никто не станет. Наша территория — то, чего облако не может в принципе, потому что
  у него нет доступа к вашим вкладкам, истории и черновикам.

## Программа «локальный AI по делу» (в работе, по срезам)

Замысел, из которого выросли срезы ниже: **локальная 9B не заменяет облако и не должна с ним
сравниваться.** Чат на ней всерьёз никто вести не будет. Зато она незаменима там, где задача
короткая, ответ жёсткой формы, шаг один — и где материал НЕЛЬЗЯ отдавать наружу: свой черновик,
своя история, подписи полей на странице. Все срезы ниже отобраны по этому признаку.

**Критерий пригодности задачи** (по нему судить и будущие идеи): короткий вход и короткий выход;
ответ жёсткой формы, который валидирует код; один шаг без плана; ошибка дёшева и видна человеку;
данные личные. Анти-критерий: если результат мысленно сравнят с облачной моделью в лоб — не брать.

⚠️ **И главный отсеивающий вопрос, дописанный по итогам среза 8: не решается ли задача обычным
кодом ЛУЧШЕ?** Формально срез 8 критерию соответствовал, а по сути — нет: каталог правил закрыт
и мал (два триггера, четыре действия), то есть правило это форма из четырёх полей, и разбор
фразы менял стопроцентную точность формы на семь попаданий из восьми плюс 6 ГБ VRAM и холодный
старт. Отдельное следствие, которое легко проглядеть: **модель в проекте опциональна**, и фича,
у которой ЕДИНСТВЕННЫЙ вход идёт через модель, у человека без скачанной модели не работает вовсе.
Правильная форма таких фич — обычный интерфейс основным путём, модель второй дорожкой «если так
быстрее». Так и сделано в `RulesSection.tsx`.

Сделано ЦЕЛИКОМ, все восемь срезов (каждый — свой коммит, все проверены живыми прогонами на
настоящей Qwen 9B):
1. **Правка своего текста в поле ввода** — ПКМ → «Править текст» (ошибки/короче/тон), вставка
   через `execCommand` с сохранением Ctrl+Z. См. «Архитектура» выше.
2. **Поиск вкладки по смыслу** в омнибоксе (`TabSearch.ts`) — замер 5 попаданий из 5.
3. **Поля форм по смыслу** (`AutofillFieldMapper.ts`) + починка детекта подписей: эвристика знала
   0 полей из 4 на форме с нестандартными подписями, стало 4 из 4.
4. **Двухполосная очередь** (`QwenQueue.ts`) — фон не обгоняет человека.
5. **«Чем занимался»** (`DayDigest.ts`) — итоги дня по истории, виджет на столе.
6. **«Вы это уже читали»** (`RelatedHistory.ts`) — связанное из своей истории в нетронутом омнибоксе.
7. **Смысловой Ctrl+F** (`SmartFind.ts`) — вторым режимом в панели поиска, 6 вопросов из 6 на
   живом замере. Попутно вскрыта и починена давняя поломка: Electron 40 не отвечает на начало
   поиска, из-за чего счётчик совпадений не появлялся до нажатия Enter (см. «Архитектура»).

⚠️ **Урок из этой же программы (поломка найдена пользователем и починена):** «Вы это уже читали»
почти никогда не показывалось — условие показа было «клик при ПУСТОЙ строке», а на открытой
странице в омнибоксе лежит её адрес. Общее правило на будущее: **условие «человек ничего не
набирал» в омнибоксе — это «пусто ИЛИ равно адресу вкладки», а не «пусто»**; проверять такие
фичи надо на реальной вкладке, а не на новой пустой.

8. **Правила-автоматизации из фразы** (`shared/rules.ts` + `RuleStore`/`RuleEngine`/`RuleParser` +
   раздел настроек `RulesSection.tsx`) — «ссылки с habr.com открывай в группе Чтение». Сделан
   четырьмя шагами, каждый со своим коммитом и своим прогоном: каталог и хранилище (33 проверки
   `npm run rules-check`) → исполнение обычным кодом (8 живых проверок) → разбор фразы моделью
   (7 из 8 на живой 9B) → экран правил (5 проверок, от фразы до сработавшего правила).
   Подробности и уроки — в «Архитектуре» выше.

Программа выполнена целиком. Что стоит делать дальше по этой линии — судить по критерию
пригодности в начале раздела: короткий вход и выход, ответ жёсткой формы, один шаг, дешёвая
и видимая ошибка, личные данные.

⚠️ **Стенд замеров `npm run ai-bench`** (`scripts/ai-bench.mjs`) — батарея задач с жёсткой формой
ответа на любой установленной модели: поиск вкладки по смыслу, смысловой Ctrl+F, разбор фразы в
правило, AI-группировка. Свой профиль во временной папке ОС + junction на боевую папку моделей
(гигабайты не копируются, снимается ПЕРВЫМ до удаления профиля). Три вещи, без которых стенд врёт
и которые уже стоили одного ложного прогона:
- **Прогрев обязателен и он же первый замер.** Половина фич гейтится `isModelWarm()` и на холодной
  модели молча отвечает пустотой — первый прогон показал 1 из 7 у поиска вкладок при нулевом
  времени ответа, то есть мерил гейт, а не модель. Греем разбором фразы (у него гейта нет).
- **Повторы (`--repeat`).** Ответ НЕ детерминирован: одна и та же фраза даёт разные разборы между
  прогонами. Однократный замер меряет везение — отсюда «шаткие» случаи отдельной колонкой.
- **Сырой ответ модели в выводе.** Без него «модель не поняла» неотличимо от «мы не так разобрали»;
  первый же прогон с логом показал, что модель ответила ВЕРНО, а отбраковал ответ наш код.

⚠️ **ПОЧЕМУ ОТВЕТ «ПЛАВАЛ» И ЧЕМ ЭТО ЛЕЧИТСЯ — разобрано до конца, не переоткрывать.**
Симптом: одна и та же фраза давала разные разборы между прогонами. Расследование (каждый пункт —
замер, а не рассуждение):
- **Сэмплинг ни при чём.** `temperature` в node-llama-cpp по умолчанию 0 — выборка жадная.
- **Остаточный контекст ни при чём.** Перед каждым прогоном `nextTokenIndex`=0,
  `stateCellsStartIndex`=-1, токенов в контексте 0. Очистка ПЕРЕД прогоном ничего не меняет
  (пробовал, откачено).
- **Квантованный KV-кэш ни при чём.** С f16 картина та же.
- **Промпт ни при чём.** Отрисованный промпт побайтно одинаков (339 токенов на всех прогонах).
- **Что видно:** прогоны 2, 3, 4 совпадают между собой ТОЧНО, а первый в процессе отличается.
  То есть вычисление детерминировано в установившемся режиме, а расходится от РАСКЛАДКИ
  ВЫЧИСЛЕНИЙ: порядок сложений с плавающей точкой зависит от разбиения на батчи, а оно — от того,
  что считалось до этого (известное свойство llama.cpp: логиты не гарантируются побитово
  одинаковыми при разном размере батча).
**Отсюда главный вывод: разница в логитах порядка 1e-4 меняет ответ ТОЛЬКО там, где модель и так
почти не уверена — где два варианта идут ноздря в ноздрю. Плавает не машина, а решение, которое
модели тяжело.** Значит лечится это промптом, а не бубном вокруг движка:
**ОДНО РЕШЕНИЕ НА ПРОГОН.** Проверено на разборе правил: выбор триггера (`site` ↔ `link-from`) был
пятым полем общего ответа и флапал на одной и той же фразе; вынесли его в отдельный короткий
прогон — стало 7 из 8 при НУЛЕ шатких случаев (было 5 из 8 и два шатких). Цена — 1.0 с вместо
0.7 с на разбор, то есть второй прогон модели; для действия, которое человек делает раз в жизни
правила, это ничто.

⚠️ **Эталон 9B (Qwen3.5-9B-Q4_K_M, три повтора, август 2026):** вкладки 6/7, Ctrl+F 5/6,
правила 7/8, группировка 3/3, итого 21/24, холодный старт 32 с, шатких случаев ноль.
Путь до этих цифр: 17/24 с двумя шаткими → 19/24 (триггер правила отдельным прогоном) →
21/24 (группировка на две фазы плюс арбитраж кодом). Оба скачка — одно и то же лекарство,
дробление решений; см. `TabOrganizer.ts` и `RuleParser.ts`.
⚠️ Проверка группировки намеренно НЕ требует «разложить половину вкладок»: фикстура набрана из
несвязанных страниц, половине не с кем группироваться, и такой порог наказывал бы за осторожность.
Проверяются ОШИБКИ (заведомо чужие пары в одной группе) — цена ошибки здесь живая вкладка человека.

⚠️ **Уроки, оплаченные замерами** — применять сразу, не переоткрывать:
- **Инструкции промпта — по-английски**, содержимое остаётся русским. Три русских формулировки
  подряд заставляли модель переписывать список обратно вместо ответа; английская заработала с
  первого раза. Так же устроены давно работающие перевод и AI-действия.
- **Если ответ должен существовать в реальности — пусть модель ВЫБИРАЕТ, а не пишет.** Номер из
  списка, который собрали мы, вместо текста своими словами: тогда результат физически взят из
  источника, врать негде, и его можно чем-то проверить (подсветить на странице, открыть вкладку).
  На этом устроены и поиск вкладки, и смысловой Ctrl+F; попроси мы «процитировать» — 9B вернёт
  пересказ, который на странице не найдётся.
- **ОДНО РЕШЕНИЕ НА ПРОГОН.** Если в одном ответе модель обязана выбрать сразу несколько вещей,
  самая трудная из них начинает флапать — и не от «случайности», а потому что на ней модель почти
  не уверена, а расклад вычислений между прогонами чуть разный (разбор — в блоке про стенд ниже).
  Вынести трудный выбор в отдельный короткий прогон дороже на один вызов и дешевле на всю
  ненадёжность: у разбора правил это дало 7/8 без единого шаткого случая вместо 5/8 с двумя.
- **У ответа должна быть словесная МЕТКА** («ANSWER: 3», «Название: 1,2,3»), а не голое число и не
  JSON: без метки модель достраивает нумерованный список, а JSON на этом корпусе ломается.
- **Разбирать только строку после метки.** Наивный разбор «любых чисел в ответе» вытаскивал номера
  из скопированного моделью перечня и выдавал их за её выбор — три уверенные подсказки, означающие
  «модель не поняла вопрос». Пустой ответ честнее выдуманного.
- **Никаких неявных загрузок модели.** Холодный старт 9B — 31 с и ~6 ГБ VRAM (замерено). Всё, что
  человек не заказал явно, идёт через `isModelWarm()` и молчит на холодной модели; явное действие
  (кнопка) ждать загрузку вправе.
- **Фоновое — фоновой полосой** (`runTabOrganizePrompt(prompt, { background: true })`).
- **Замер на временном профиле БЕЗ модели бессмысленен**: приложение откатывается на бандл
  `resources/models/gguf`, где лежит EuroLLM-1.7B, и меряется поведение переводчика на 1.7B.
  Рецепт проверки: свой `--user-data-dir` в scratchpad + junction `models` на боевую папку
  (`mklink /J`, файл только читается), прогрев модели через открытие AI-панели, и только потом
  замер. ⚠️ После прогонов проверять, не остались ли висеть процессы `electron.exe`: они держат
  VRAM, из-за чего следующий запуск получает крошечный контекст и генерация падает на ровном месте.

## Безопасность паролей — бэклог усиления (аудит 2026-07-25)

Прямых утечек нет, архитектура надёжная (шифрование AES-256-GCM + safeStorage,
plaintext не пишется на диск/в логи, к веб-страницам API не пробрасывается,
origin из доверенного `wc.getURL()`, автофилл гейтится top-frame с обеих сторон).
Реализовать по мере готовности (порядок — по значимости):
1. **KDF экспорта.** `VaultCrypto.encryptWithPassphrase` использует `scryptSync`
   с дефолтами Node (N=2¹⁴) — слабовато для переносимого файла при слабой фразе.
   Поднять до N=2¹⁶–2¹⁷ (r=8,p=1) + явный `maxmem`, параметры писать в конверт
   (`v:2`, старые файлы читать по-старому).
2. **Буфер обмена.** `PasswordManager.copyField` чистит буфер через 30с, но
   Windows Clipboard History / облачный буфер могут сохранить пароль. Писать в
   буфер с флагом «исключить из истории» (`ExcludeClipboardContentFromMonitor
   Processing`/`CanIncludeInClipboardHistory=0`) — Electron не умеет, нужен
   маленький нативный/PowerShell-хелпер за платформенным интерфейсом.
3. **Hello и для автозаполнения (опция).** Сейчас Hello-гейт (см. `osAuth.ts`)
   закрывает только просмотр/копирование в настройках; автофилл в страницу и
   «Заполнить» из поповера не гейтятся (как у Chrome/Яндекса). Добавить тумблер
   «требовать Hello и для автозаполнения».
4. **Приватность favicon.** ЧАСТИЧНО СНЯТО: список в настройках теперь свёрнут по
   умолчанию (`listOpen` в `PasswordsSection.tsx`), и при открытии настроек запросов
   на домены сохранённых аккаунтов больше нет вовсе — они уходят только когда человек
   сам раскрыл список. Осталось: раскрытый список по-прежнему ходит на ВСЕ домены сразу
   (а не только на видимые строки), и запрос идёт через default-сессию, то есть может
   нести куки. Доделать: сессия без кук + ленивость по строкам.
5. **Окно доверия Hello.** Сейчас глобальное 5 мин на все записи — сделать
   настраиваемым/короче при желании.
6. **Метаданные в открытом виде.** В `passwords.sqlite` `origin/url/username/
   title` — plaintext (шифруются только `secret`/`notes`), как у Chrome. Список
   аккаунтов виден при доступе к файлу; шифрование метаданных — если понадобится.
