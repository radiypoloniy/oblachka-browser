# Как участвовать

Проект живёт по правилам из [CLAUDE.md](CLAUDE.md) — это не документация «для галочки», а
работающий свод: там записаны решения, каждое из которых оплачено замером или поломкой у
пользователя. Прочитайте его до первой правки.

## Сборка

Windows x64, Node 22.6+ (нужен разбор `.ts` голым node для проверок).

```bash
npm install          # postinstall пересоберёт better-sqlite3 под ABI Electron
npm run dev          # Vite + Electron одновременно
npm run build        # прод-сборка
npm start            # запуск собранного
```

Часть возможностей требует отдельной загрузки: `npm run download-xray` (VPN),
`npm run download-translation-models` (перевод страниц), модель для локального ИИ качается из
интерфейса. Без них браузер работает, просто эти функции честно сообщают, что недоступны.

## Что обязано быть зелёным

```bash
npx tsc -p tsconfig.json --noEmit      # типы renderer
npx tsc -p electron/tsconfig.json      # типы main
npm test                               # все проверки (~17 с)
```

Это же гоняет `.githooks/pre-commit` — он ставится сам при `npm install`. Пропустить осознанно:
`git commit --no-verify`.

Отдельно, перед правками в `electron/` и перед релизом:

```bash
npm run drive        # живые прогоны: поднимают НАСТОЯЩЕЕ приложение (~100 с)
```

## Четыре сторожа, и что каждый держит

| Сторож | Что не пропускает |
| --- | --- |
| `conventions-check` | фиолетовый в системных цветах, `ipcRenderer` в renderer, необъяснённый `any`, значимые импорты в проверяемых модулях `shared/` |
| `contract-check` | мёртвые каналы IPC, `invoke` без `handle`, арность, канал строкой мимо `IPC.*` |
| `structure-check` | рост файлов и функций сверх порогов |
| `lint-check` | условный вызов хука, забытая зависимость эффекта, забытый `await` |

Два последних — **храповики**: новый код обязан быть чистым, а файл из базы не имеет права стать
хуже своей записи. Стало лучше — зафиксируйте новый уровень (`--update`), назад дороги нет.

⚠️ Если сторож мешает вашей правке, **платите выносом, а не поднятием базы**. Это не формальность:
поднятая база — это разрешение расти дальше, выданное самому себе.

## Проверки

Новая проверка подхватывается прогоном сама — достаточно положить `scripts/<имя>-check.mjs`.
То же с живыми: `scripts/<имя>-drive.mjs`.

Правите чистую логику в `shared/` — добавьте случай в соответствующую проверку. Особенно если
правка чинит баг: **случай из жизни в проверке дороже трёх выдуманных**.

Проверка, которая не краснеет от возвращённого бага, — не проверка. Заведя новую, верните баг
руками и убедитесь, что прогон падает. Так сделаны `calendar-flicker-drive` и `omnibox-drive`.

`npm run mutate` отвечает на вопрос, которого не задаёт ни один прогон: **а проверки вообще
что-нибудь держат?** Логику портят по одному месту и смотрят, упадёт ли хоть одна. Выживший
мутант — место для глаз, а не автоматическая задача: часть мутаций эквивалентна исходному коду.

## Как писать код

- **Чистота и читаемость важнее ранней оптимизации.** Оптимизация — только там, где измеримо
  тормозит на живых замерах.
- **TypeScript strict.** `any` и `@ts-ignore` — только с комментарием, почему иначе нельзя.
- **Комментарии по-русски и объясняют ЗАЧЕМ**, а не ЧТО. Знак ⚠️ помечает места, где очевидное
  решение неверно, — там почти всегда стоит разбор живого случая. Не удаляйте такие комментарии,
  не разобравшись: они дороже кода, который описывают.
- **Одна фича за заход.** Две сразу — и при поломке не понять, что виновато.
- **Не рефакторьте то, о чём не просили.** Узкая задача — узкая правка.
- Зависимости — только по явной нужде и с объяснением, зачем.

## Осторожно: данные пользователя

Автосейв сессии, история, закладки, сейф паролей — это реальные данные живых людей.

⚠️ **Никогда не удаляйте пользовательские sqlite/json в `userData`**, чтобы «пересоздать после
ошибки». Это уже случалось: `unlink` при сбое нативного модуля стёр боевые пароли, закладки и
историю. Не открылось — функция выключается, файл остаётся.

Диагностику и замеры запускайте на изолированном профиле (`npm run stand`), а не на боевом.

## Коммиты

Сообщения по-русски, в стиле `тип(область): суть`. В теле — **почему**, а не перечень файлов:
что было сломано, какой механизм за этим стоял, какой размен принят. Хороший образец —
`git log` проекта.
