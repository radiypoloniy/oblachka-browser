# Равноправные окна Oblako: исследование и план

Дата: 4 октября 2026. Статус: реализованы этапы 1 (адресация) и 2 (жизненный цикл), см. `window-routing-validation.md` и `window-lifecycle-validation.md`. Сессия нескольких окон и остальные этапы ещё впереди. Раздел исследования ниже описывает исходное состояние до этих изменений.

## Решение в одном абзаце

Каждое окно браузера получает одинаковые вкладки, сайдбар, закрепления, группы, split, поиск и AI-панель. Дерево вкладок и вид интерфейса принадлежат окну. Хранилища профилей, VPN и AI-runtime принадлежат приложению. Сессию всех окон сохраняет один координатор. Для закреплений предлагается дополнительная защита: закрытое окно с закреплениями сохраняется как продолжаемая сессия и возвращается при следующем запуске. Это продуктовое предложение Oblako, а не описание стандартного поведения Chrome.

## Что обнаружено в текущем коде

| Область | Фактическое состояние | Почему мешает равноправным окнам |
| --- | --- | --- |
| Создание | `electron/main.ts:createWindow(role)` создаёт свой chromeView и TabManager для каждого окна. `electron/ipc/windows.ts` и `window/wireTabs.ts` создают дополнительные окна с ролью `light`. | Основа уже есть; новый стек браузера строить не требуется. |
| Интерфейс | `src/App.tsx` получает роль через IPC и передаёт `isLightWindow` дальше; имеются ограничения хаба, организации и выбора профиля. | Недостаточно заменить одну проверку: все возможности должны получить корректный оконный адресат. |
| Сессия | Только `main` создаёт SessionManager, читает файл и становится его владельцем через `setOwner`. Реальная версия формата — **5**, дебаунс — 1500 мс, запись через временный файл и rename. | Состояние дополнительных окон не сохраняется. Несколько SessionManager на одном пути затрут друг друга. |
| Закрытие | `main.ts`, обработчик `win.close`, выставляет общий `isShuttingDown` и останавливает VPN при закрытии главного окна. | Живое дополнительное окно теряет сервис приложения; дальнейшие действия некоторых функций считаются действиями во время выхода. |
| IPC | WindowRegistry уже находит владельца chromeView по sender; большинство команд используют `tabsOf/winOf`. Но сохраняются `mainContext`, `mainTabs` и fallback на первое окно. | После исчезновения главного окна часть функций теряет адресат или выбирает чужое окно. |
| AI-панель | `aipanel/instances.ts` хранит отдельные views, но `light` получает `kind: apps`; `chatPanel()` выбирает главное окно. | Полноценный чат есть только в одном окне. |
| Чат страницы | `aipanel/tabChat.ts` имеет общий `activeTabId/url/title`, общую функцию `pageWcOf`, контексты по tabId. `window/tabManager.ts` передаёт снапшоты панели только от главного окна. | Простое снятие `isMain` заставит окна перезаписывать активную вкладку друг друга. |
| Локальная модель | `TranslationService.ts` уже использует общую `QwenQueue.ts`: пользовательская и фоновая полосы, одна выполняющаяся задача, отмена ожидания через AbortSignal. Чат локального провайдера проходит через ту же очередь. | Новая очередь на каждое окно опасна и не нужна. Не хватает владения задачами и адресной отмены/статуса. |
| Перевод и организация | `PageTranslateManager.ts` и `TabOrganizer.ts` держат один `tabManagerRef`; `wireTabs.ts` подключает их внутри `isMain`. | Повторный `setTabManager` лишь подменит главное окно последним созданным. |
| Чат хаба | `HubChatManager` хранит контексты по tabId; `window/tabManager.ts` вызывает `pruneClosedTabs` со снапшотом одного окна. | При снятии ограничений снапшот окна A может удалить чат живой вкладки окна B. |
| Перенос | `TabManager.detachTabForMove/adoptTab` уже передают живую view или описание спящей вкладки. При принятии создаётся **новый tabId**, а detached-описание не содержит полного состояния закрепления/чата. | Нужна явная политика переноса метаданных и транзакция сохранения; иначе теряются закрепление или связь с чатом. |
| Поповеры | Часть уже пооконная, часть хранит одну view и `attachedWin` — например Translate/Search/Site/Downloads. | Закрытие/переключение в одном окне не должно снимать UI или результат другого. |

Общая инфраструктура уже значительна. Работу следует вести заменой конкретных зависимостей от «главного окна», а не переписыванием TabManager и хранилищ.

## Опыт других браузеров

1. **Firefox:** восстанавливает окна и вкладки, включая закреплённые; приватные окна исключены. Документация отдельно предупреждает: при последовательном ручном закрытии окон восстанавливаются вкладки последнего закрытого окна. Значит, «восстановить последнюю сессию» само по себе не решает вопрос о закреплениях во втором окне. Источник: [Firefox Session Restore](https://support.mozilla.org/en-US/kb/restore-previous-session).
2. **Chrome:** документирует режим «Continue where you left off». Эту страницу нельзя использовать как гарантию сохранения закреплений каждого ранее закрытого окна: такого обещания в ней нет. Источник: [Chrome: startup page](https://support.google.com/chrome/answer/95314?hl=en).
3. **Vivaldi:** позволяет сохранять сессию текущего окна или всех окон и делает автоматические резервные сессии. Полезная идея для Oblako — хранить целые деревья окон и иметь восстановимые снимки. Источник: [Vivaldi Sessions Panel](https://help.vivaldi.com/desktop/panels/sessions-panel/).
4. **Vivaldi:** отдельно защищает закреплённые вкладки от обычного закрытия и поддерживает ленивое восстановление. Это аргумент в пользу явной долговечности закрепления и восстановления без загрузки всех страниц. Источник: [Vivaldi Pinned Tabs](https://help.vivaldi.com/desktop/tabs/pinned-tabs/).

Эти источники описывают UX и сессии браузеров. Предлагаемое устройство AI основано на существующем коде Oblako; внутренние AI-очереди других браузеров здесь не предполагаются.

## Предлагаемое поведение пользователя

Закрепление — свойство вкладки конкретного окна. Новое пустое окно не копирует закрепления остальных окон: иначе появятся дубли, конкурирующие страницы и вопрос, где снимается закрепление. Перенос закреплённой вкладки переносит само закрепление вместе с профилем и чатом.

| Действие | Предлагаемый результат |
| --- | --- |
| Открыть новое окно | Полный интерфейс, новый независимый набор вкладок, те же общие данные приложения. |
| Закрыть A, оставить B | B продолжает работать; VPN и модель живут. A доступно в «Недавно закрытых окнах» целым деревом. |
| Закрыть окно с закреплениями | Дополнительно сохранить его как продолжаемое окно. При следующем запуске восстановить его дерево и закрепления; никаких переносов в другое окно. |
| Последовательно закрыть A с закреплениями, затем B | При запуске вернуть B как последнюю открытую сессию и A как продолжаемое окно. Один и тот же снимок не восстановить дважды. |
| Выбрать «Выйти из Oblako» | Сохранить набор всех открытых окон одним снимком **до** их уничтожения. При запуске вернуть этот набор плюс ранее закрытые продолжаемые окна. |
| Закрыть обычное окно без закреплений | Оно остаётся в ограниченном списке недавно закрытых; само при следующем запуске не появляется, кроме последнего окна сессии. |
| Восстановить закрытое окно вручную | Открыть один экземпляр; убрать соответствующую запись из закрытых, сохранить его постоянный windowId. |
| Снять все закрепления и закрыть окно | Оно получает обычную политику закрытого окна. |
| Удалить сохранённое окно с закреплениями | Отдельное явное действие с предупреждением о потере сохранённого набора; не удалять автоматически по лимиту обычной истории окон. |
| Падение процесса / питание | Вернуть последний успешно записанный набор окон; несохранённый интервал ограничен дебаунсом. |
| Приватная вкладка, в том числе закреплённая | Не писать в сессию и закрытые окна. Окно только с приватными вкладками не создавать заново из снимка. |

Сохранение закрытого окна с закреплениями целиком — осознанный выбор: группы и обычные вкладки дают контекст работы. Альтернатива — возвращать только закрепления; она легче по UX, но обрезает контекст. Рекомендация для первого варианта реализации — сохранять целое окно и восстанавливать его страницы спящими.

На macOS закрытие последнего окна не равно Cmd+Q: приложение может оставаться живым. Продолжаемые окна автоматически возвращаются при новом запуске процесса; Dock/`activate` при живом процессе открывает обычное окно, не возвращая сразу все закрытые. Геометрию восстанавливать с проверкой доступных экранов; отключённый монитор не должен оставлять окно за пределами рабочего стола.

## Архитектура

### Окна и общие сервисы

`BrowserWindowContext` получает постоянный UUID `windowId` (Electron `win.id` недостаточен для перезапуска), chromeView, TabManager и контроллеры UI. BrowserWindowRegistry хранит владельцев всех зарегистрированных chrome/overlay/page views и последние сфокусированные окна.

Оконные команды обязаны определять окно по sender и проверять принадлежность tabId. Если sender не зарегистрирован, команда отклоняется, а не отправляется в первое окно. Для внешних ссылок/запуска из мессенджера нужна отдельная политика: последнее сфокусированное обычное окно, либо создание нового. Служебные и OAuth-окна в восстановление браузерных окон не включать.

Общие на приложение: настройки, менеджеры профилей/секретов, история и закладки в существующих границах профилей, загрузки, VPN, модель, соединения AI и очередь. Пооконные: дерево вкладок, активная вкладка, split, sidebar, геометрия, док AI, поиск и привязки поповеров. Не создавать второй SQLite-менеджер на тот же файл ради нового окна.

`mainWin/mainTabs/mainChromeView/mainSess` и роль `main/light` устранять постепенно. Прогрев общих сервисов запускать один раз на процесс; прогрев UI — по потребности конкретного окна. Замена `isMain` на `true` повсюду недопустима: она дублирует регистрацию колбэков и глобальные действия.

### Сессия: один писатель, много окон

Ввести `BrowserSessionCoordinator` с единственным владельцем файла. Он принимает снимки зарегистрированных окон и собирает общий документ; оконный SessionManager больше не пишет независимо в один `session.json`.

Предлагаемая v6-оболочка:

```ts
interface BrowserSessionV6 {
  version: 6;
  savedAt: string;
  app?: string;
  revision: number;
  lastFocusedWindowId: string | null;
  windows: SavedBrowserWindow[];
  closedWindows: SavedClosedWindow[];
}
// SavedBrowserWindow: постоянный windowId, геометрия/состояние окна,
// SessionSnapshot текущего дерева, признак открытия при запуске.
// SavedClosedWindow: тот же снимок + closedAt + причина/политика продолжения.
```

Дерево `SessionSnapshot` сохранить максимально близко к нынешнему: pinnedTabs, nodes и activeRef. Во время реализации отдельно проверить текущую URL-идентификацию activeRef для двух одинаковых адресов; при необходимости в v6 перейти к сохраняемому tabId с отдельной миграцией, а не скрыто менять смысл старого поля.

Миграция: читать v1–v5 существующими проверками → один восстановленный windowId → валидированная v6. До первой записи v6 сохранить неизменную резервную копию исходного файла. Не начинать автосейв, пока весь набор окон не зарегистрирован и восстановлен: первое поднявшееся окно иначе запишет неполную сессию.

Запись: один writer, temp → rename, последняя корректная резервная копия, обработка отказа диска. Ошибка загрузки не означает пустую сессию, которую разрешено сразу записать поверх исходника. Ошибка финального сохранения должна быть видимой и давать возможность повторить/отменить выход. Восстановление после повреждения — из последнего валидного снимка; неизвестная будущая версия сохраняется отдельно, как в текущем механизме.

Перенос между окнами — одна транзакция координатора: исходное окно удаляет вкладку, целевое подтверждает принятие, затем сохраняются оба. При отказе создать окно или принять view восстановить исходного владельца. Снимок между detach и adopt не публиковать. Либо сохранять стабильный tabId при переносе, либо явно переносить чат, состояния перевода, профиля и закрепления в новую идентичность; предпочтительно стабильное id.

### Завершение приложения

Состояния координатора: `running → preparingQuit → quitting`, плюс возврат в `running` при отмене закрытия. Закрытие одного окна не выставляет общий флаг выхода. Перед уничтожением окна получить его снимок и записать/обновить продолжаемое или закрытое окно.

При явном выходе сначала собрать все живые окна одним набором и синхронно зафиксировать его; последующие `close` не должны превратить этот набор в последовательность отдельных закрытых окон. Отдельно обработать veto `beforeunload`, отмену выхода и обновление приложения. VPN/AI останавливать один раз, когда действительно завершается приложение. Оконные views и таймеры удалять при закрытии только своего владельца.

Electron документирует различие `before-quit`, `window-all-closed` и выхода через `app.quit`; при системном завершении Windows часть quit-событий не вызывается. Поэтому периодический автосейв обязателен, финальное событие само по себе не гарантирует сохранность. Проверить Windows `query-session-end/session-end` за платформенным адаптером, а также существующий путь автообновления. Источник: [Electron app lifecycle](https://www.electronjs.org/docs/latest/api/app).

### AI: общий runtime, отдельные контексты

Оставить существующий QwenQueue и единственный локальный runtime. Окна не загружают отдельные копии модели; смена/выгрузка модели синхронизируется тем же механизмом. Платформенный бюджет памяти остаётся за существующей абстракцией runtime, отдельно для Windows GPU и macOS unified memory.

Каждый запрос получает `jobId`, `windowId`, `tabId` при наличии, идентификатор поколения страницы/диалога, роль AI, полосу очереди и AbortController. Провайдера и конфигурацию фиксировать по понятной политике; изменение маршрута не должно посреди стрима подменять уже выполняющуюся задачу.

Пользовательские запросы разных окон идут FIFO в существующей пользовательской полосе; фон работает только после неё. Активное окно не вытесняет задачу другого окна автоматически. В UI показывать «В очереди», «Выполняется», возможность отменить, и при необходимости «Локальная модель занята в другом окне». Прогресс и токены отправляются только владельцу jobId. Лимит одной выполняющейся локальной задачи сохраняется.

Чат панели получает пооконный controller: активная вкладка и ссылки на её страницу вычисляются из владельца панели, а не глобального `activeTabId`. Контекст разговора принадлежит стабильному tabId; перенос страницы переносит разговор. Разговор другой вкладки можно продолжить, но его результат не должен сам переключать активную вкладку или появляться в чужой панели.

Закрытие окна/вкладки отменяет только его задачи. Ожидающие задачи удаляются из очереди. Текущий native-run прерывается через поддерживаемый abort; если конкретный backend не умеет прерывать, задача дорабатывает без доставки результата, runtime не уничтожается из-под генерации. Новая навигация/сброс диалога меняет поколение: поздний ответ нельзя применить к новой странице. Исключение задачи освобождает очередь для остальных окон.

`TabOrganizer` принимает TabManager конкретного окна аргументом; `PageTranslateManager` разрешает вкладку через реестр. При чистке HubChat учитывать объединение живых вкладок **всех** окон. Не рассылать текст переписки общими broadcast-пушами. Сетевые провайдеры могут работать параллельно с локальным и между окнами, но с общей политикой ограничения запросов провайдера; текущий локальный queue не превращать в блокировку всей сети.

Эмбеддинги/группировку проверить отдельно: renderer-worker на каждое окно может дублировать память модели. Сначала измерить два окна; только при подтверждённом расходе вынести общий embedding-service в выделенный процесс/worker с оконными requestId. Не включать такой перенос в первый этап без измерений.

## Этапы реализации: одна законченная фича за заход

1. **Адресация окон.** Инвентаризация всех role/isMain/mainContext/global setter и владельцев IPC, явный resolver оконных views, политика внешних ссылок. Проверка: два окна выполняют команды строго в своём дереве; закрытие первого не ломает второе. UI пока остаётся прежним.
2. **Жизненный цикл сервисов.** Убрать остановку VPN/общий shutdown при закрытии отдельного окна; сохранить прежнюю защиту от служебных скрытых окон, удерживающих процесс. Проверка: первое/последнее окно, явный выход, отмена beforeunload, повторный запуск, macOS activate.
3. **Сессия нескольких окон.** Координатор, v6, backup/migration, восстановление, закрытые и продолжаемые окна, геометрия. Это самый рискованный этап: до него коммит и проверка на копии/пустом профиле обязательны как мера сохранности. Проверка миграций и отказов до включения в основной профиль.
4. **Одинаковые вкладки и инструменты.** Убрать ограничения `light` в UI после подключения адресных команд. Группы, закрепления, split, история/закладки/загрузки, профили и хоткеи. Перенос должен сохранять метаданные и атомарный снимок обоих окон.
5. **AI в любом окне.** Пооконные контроллеры панели, перевод/организация, владение jobs, адресные статусы/отмена, объединённая чистка чатов. Общий runtime и очередь остаются одними. Проверка с настоящей моделью и ошибкой одного запроса.
6. **Оверлеи и завершение перехода.** Каждый singleton-поповер либо становится пооконным, либо получает явную безопасную политику единственного владельца и адресного закрытия. Удалить оставшиеся роли и обходы к main, обновить документацию. Полная матрица функций в двух окнах.

После каждого изменения: `npm run build`, `npx tsc -p tsconfig.json --noEmit`, `npx tsc -p electron/tsconfig.json`. Живые проверки — через `scripts/isolated-stand.mjs`; старый `smoke-test.mjs` открывает настоящий профиль и для этой работы не подходит. Изменения сессии способны потерять вкладки, а работа с VPN-процессом — нарушить соединение; перед реализацией этих этапов отдельно предупредить и сохранить исходное состояние.

## Матрица приёмки

- Два/три окна: одинаковые доступные функции, независимые active/sidebar/split/AI-док; общие данные обновляются во всех окнах.
- В B создать закрепления и группу, закрыть B, продолжить A, закрыть A, запустить: закрепления B сохранены, правильные деревья возвращены без дублей.
- Явный выход при трёх окнах и перезапуск: восстановились три окна, порядок, закрепления, split, профили и доступная геометрия.
- Закрыть первое созданное окно: второе может открыть AI, перевести страницу, группировать вкладки; VPN продолжает работать.
- Переезд обычной/закреплённой/спящей вкладки: профиль, чат и закрепление сохранены; неудачный adopt возвращает вкладку; сбой сохранения не оставляет её между окнами.
- Два одинаковых URL в разных окнах и в одном окне: активность/чат/отмена адресуются по идентичности, не только по URL.
- Одновременные AI-задачи A/B и фон: один локальный native-run, пользовательская очередь раньше фона, отмена A не отменяет B, ошибка A не блокирует очередь.
- Закрытие, навигация и сброс чата во время генерации: поздние результаты не меняют новое состояние; перенос вкладки не отправляет текст прежнему окну.
- В v6 и backup нет приватных URL/чатов/содержимого; закрытие приватной вкладки A не очищает данные ещё живых приватных вкладок B. Последнюю приватную вкладку считать по всему приложению.
- v1–v5, битый JSON/узел, будущая версия, нехватка места/отказ rename, падение между записью и rename: исходная корректная сессия сохраняется, есть восстановление и понятная ошибка.
- Ctrl+N, ссылки из внешнего приложения, OAuth popup, обновление, Windows завершение сеанса, отмена закрытия, macOS Cmd+Q/activate и отключённый монитор.

Готовность: любое обычное окно способно полноценно работать после закрытия любого другого; порядок закрытия не теряет закрепления; AI-задачи не делят контекст страницы и не конфликтуют в runtime.
