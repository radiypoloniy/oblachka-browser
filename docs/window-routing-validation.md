# Окна: первый этап адресации

4 октября 2026. Первый этап плана `equal-windows-plan.md`; роли окон, формат сессии и AI-контексты ещё прежние.

## Изменения

- Оконные `tabsOf`, `winOf`, `chromeOf` вынесены в `electron/window/ipcRouting.ts`. При неизвестном/закрытом отправителе возвращают null. Резервного пути в главное окно нет.
- WindowRegistry явно регистрирует chromeView, AI-панель и поповер буфера. Привязка работает и для скрытой view, допускает переезд и прекращается при закрытии владельца. WeakMap не удерживает уничтоженные webContents.
- Страницы TabManager разрешаются по актуальному владельцу; веб-приложения панели и графа регистрируются отдельно. Эти страницы не получают права выполнять команды UI.
- Разрешения и вопросы о повторной загрузке идут владельцу страницы. Если владельца нет, незавершённый запрос отменяется, а не показывается в другом окне.
- Общие уведомления, внешние ссылки и фоновая индексация выбирают последнее сфокусированное браузерное окно. При закрытии оно удаляется из порядка фокуса. Служебные окна не становятся браузерным адресатом.
- Удалены глобальные `mainWin/mainChromeView`, более не нужные после устранения IPC-fallback. `mainTabs/mainSess` пока нужны старому сохранению сессии.

## Проверки

`node scripts/window-routing-drive.mjs` запускает два настоящих окна на временном профиле через существующий isolated-stand и проверяет:

1. Вызов createTab из chrome каждого окна создаёт вкладку только в его дереве.
2. Чужой tabId не активирует вкладку другого окна.
3. Неизвестный отправитель не получает ни окно, ни TabManager, ни chrome.
4. Интерфейсная view получает владельца после регистрации и меняет его при явной перепривязке.
5. Страница обычной вкладки и зарегистрированного веб-приложения разрешается для страниц, но не для команд chrome.
6. Порядок фокуса выбирает A/B; после закрытия B остаётся A.
7. Всё ещё живая view закрытого окна не получает резервного владельца.
8. Зарегистрированный overlay может создать вкладку своего окна через настоящий handler TAB_CREATE.
9. Поздняя отправка в уничтоженный webContents не бросает и не перенаправляется другому окну.

Сборка и проверки типов обоих таргетов обязательны перед коммитом; полный `npm test` запускает pre-commit hook. Hook не отключается. Все живые проверки используют пустые временные профили.

## Границы этапа

Сохранение дополнительных окон, долговечность закреплений, shutdown/VPN, общие activeTab AI-контексты и singleton-поповеры остаются следующим этапам плана. Дополнительные окна пока имеют прежнюю роль light.

Прочие специализированные оверлеи продолжают использовать свои текущие sender-resolvers. Их полное объединение с реестром и проверка взаимодействия между окнами относится к этапу оверлеев; в этом коммите их бизнес-логика не меняется.

До изменения дискового формата потребуется коммит исходного состояния, резервная копия и проверка миграций на копии/пустом профиле. Следующий этап — жизненный цикл общих сервисов: закрытие первого окна должно сохранить VPN и корректное состояние выхода остальных окон.
