# История: отдельный читатель SQLite/FTS

Точка до этого этапа — `bbc1316`. Изменение не требует миграции данных.

## Что изменено

Обычные IPC-чтения истории, подбор кандидатов для умного/объединённого поиска и связанных страниц, расчёт охвата индекса выполняются в Node worker через read-only соединение. Запись визитов/текста, импорт, очистка и миграции остаются у прежнего HistoryManager. Синхронные методы сохраняются для внутренних потребителей и изолированных :memory:-проверок.

SQL для последних посещений, подстрочного поиска и FTS, а также построение стеммированного MATCH теперь общие для синхронного и отдельного читателя. Лексика и FTS читаются внутри одной короткой транзакции. Соединение не держит долгоживущий снимок между запросами. Для охвата строки обходятся внутри worker без передачи большого массива в main.

У каждого экземпляра HistoryManager свой читатель и путь базы. После минуты без запросов поток прекращается; новый запрос открывает его снова. Закрытие/отказ потока отклоняет ожидающие запросы; повторный запрос может создать новый поток. Отключённый native SQLite сохраняет прежние пустые ответы.

Повторный клик при незавершённом подборе связанных страниц присоединяется к той же работе. Вкладка библиотеки привязана к activeId, а размонтирование истории инвалидирует поколение запросов: поздний ответ прежнего профиля не возвращает его записи в кэш.

## Измерения

`node scripts/history-smart-bench.mjs --reader` сравнивает выдачу с `history-smart-after.json`. Полные данные и 12 отдельных отсчётов каждого сценария — в `history-read-worker.json`.

| Посещений / фрагментов | Main-таймер при контентном поиске, p95 до | Main-таймер после | Время самого подбора, медиана после |
|---:|---:|---:|---:|
| 10 000 / 9 000 | 59,6 мс | 13,6 мс | 49,5 мс |
| 100 000 / 45 000 | 333,5 мс | 15,2 мс | 241,6 мс |
| 500 000 / 90 000 | 739,5 мс | 16,6 мс | 563,8 мс |

Расчёт охвата максимального корпуса занял 2275,9 мс, но контрольный main-таймер сработал через 15,2 мс. Это измерение доступности event loop через main-инспектор, не задержка ввода и не FPS. На него влияют планировщик, CPU-конкуренция и CDP. Время выполнения SQL не стало мгновенным: устранена длительная занятость main, а не стоимость поиска как таковая.

На трёх корпусах совпали все 12 наборов кандидатов, 48 вариантов выдачи при детерминированном реранке и расчёты охвата. Новая запись текстового фрагмента была видна уже существующему читателю.

## Регрессии

`node scripts/history-reader-check.mjs` использует только временные профили и проверяет:

- эквивалентность обычного поиска и кандидатов, включая русский стемминг и спецсимволы;
- пустые ответы до инициализации базы;
- две базы с пересекающимися id: ответы не смешиваются;
- видимость новой записи, замену текста с исчезновением прежнего FTS-совпадения;
- удаление во время запроса, последующее чтение, полную очистку и независимость второго профиля;
- завершение ожидающего Promise при закрытии читателя и успешное повторное открытие;
- настоящие renderer → preload → IPC методы истории;
- удержанный ответ профиля A, переход в B, получение позднего A и повторное открытие B с удержанным чтением: кэш показывает только B;
- запуск worker из временного ASAR с собственными зависимостями и better-sqlite3, распакованным аналогично конфигурации установщика.

`history-search-reuse-check.mjs` дополнительно проверяет повторный клик ещё во время SQL: один подбор и один реранк, второй вызов получает итог.

ASAR-проверка не заменяет установку полного инсталлятора. Рабочая история не использовалась; GGUF и модельный реестр для необязательного AI-прогона не меняются в пользовательском профиле.

`node scripts/history-smart-bench.mjs --reader --ai-only --live-ai` прошёл с настоящей Qwen3.5 4B и файловой базой, читаемой новым потоком. Холодный поиск — 29,85 с, прогретый — 269,4 мс. В обоих случаях повторился прежний неверный номер кандидата; защита вернула одинаковые страницы 1 и 3 с degraded=true. Это проверка сохранения fallback, а не свидетельство успешного AI-отбора.

## Ограничения

Запись и полная индексация пока остаются в main; длинные миграции и старт полного бэкфилла этим этапом не исправлены. Поиск по-прежнему может ждать выполнения SQL или общей очереди модели. Отмена устаревшей работы до её запуска — отдельный следующий этап. Существующий неверный номер кандидата от Qwen и холодная загрузка модели тоже не исправляются переносом чтений.

Итоговый npm test: 119 из 120 файлов прошли, 3557 успешных ассертов. Единственное падение — прежние семь превышений structure-check в тех же файлах, что до этого этапа. Линтер и все функциональные проверки прошли. Пороги не менялись, новых превышений нет. npm run build, обе проверки TypeScript и git diff --check прошли.

Для коммита документируется исключение pre-commit из-за прежнего structure-check после отдельного выполнения перечисленных проверок.
