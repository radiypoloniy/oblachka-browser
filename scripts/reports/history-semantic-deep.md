# Углублённая проверка смыслового поиска — 2 октября 2026

Рабочий поиск не изменён. Стенды используют временный профиль, настоящие
SQLite/worker и установленную Qwen3.5 4B Q4_K_M. Пользовательская история
не читалась. Новые зависимости, индексы и модели не добавлены.

## Что проверено

29 страниц, 14 запросов, два прохода: 56 опытов расширения запросов и
32 отдельных вызова реранкера. Первый проход генерирует один вариант перед
двумя; второй меняет порядок. На отдельных небольших наборах кандидатов
второй проход также разворачивает порядок страниц. Это проверка устойчивости,
а не доказательство причинного влияния позиции: меняется и состояние модели.

Корпус дополнен парами Linux/Windows, локальное/облачное распознавание,
Prius/Corolla, русский/английский материал, 3-2-1/3-2-9. Есть страница с
инструкцией модели внутри текста и вопросы, на которые ответа нет.
Новые пары не использовались для выбора проверяемого строгого промпта;
проверка небольшая и синтетическая, её нельзя считать оценкой всей истории.

## Одна формулировка быстрее, но теряет полезные ответы

Одинаковый общий промпт расширения: один JSON-параметр `query`, максимум
48 токенов, против двух `first/second`, максимум 96. Затем реальные сборщик
кандидатов и текущий реранкер; исходные кандидаты сохраняются первыми.

| Метрика | Один вариант | Два варианта |
| --- | ---: | ---: |
| Положительных опытов | 24 | 24 |
| Подходящая страница попала в кандидаты | 20/24 | 24/24 |
| Подходящая страница попала в ответ | 20/24 | 24/24 |
| Опыты с явно запрещённой страницей | 8/28 | 8/28 |
| Ложный ответ на отсутствующую тему | 2/4 | 2/4 |
| Генерация, медиана | 1023 мс | 2464 мс |
| Генерация, p95 | 1142 мс | 2689 мс |
| Дополнительное чтение, медиана | 1,26 мс | 1,87 мс |
| Дополнительное чтение, p95 | 2,21 мс | 4,04 мс |
| Дополнительные чтения за весь прогон | 28 | 56 |

Ошибок формата расширения и degraded-ответов здесь нет. Холодная загрузка
модели заняла 32,4 с; время генерации в таблице измерено уже на тёплой модели.
Это цена только расширения, без последующего реранка. Быстрые чтения относятся
к 29 страницам: на сотнях тысяч записей эти значения не подтверждены.

Один вариант в обоих проходах повторил исходный вопрос про потерю файлов
вместо термина «резервное копирование». Нужная страница не нашлась, а ИИ
выбрал батареи. Для полива первая формулировка «полив растений с толстыми
листьями» ничего не нашла; второй вариант «когда поливать суккуленты» восстановил
ответ. Меньший лимит вывода дал ускорение, но качеством жертвовать нельзя.

Разметка учитывает два допустимых документа про правило 3-2-1 и две английские
заметки. Изначальная метрика выбора единственной именованной страницы давала
18/24 и 22/24; пересчёт по этим допустимым альтернативам — 20/24 и 24/24.
Сырые ответы не менялись, `namedTargetSelected` сохранена отдельно.
Нарушения ограничений считаются только по явно размеченным `forbidden`;
это нижняя оценка ошибок, не полная точность выдачи. Например, ошибочная
батарея для вопроса о файлах в эту метрику не включена.

## Строгий промпт нельзя переносить в продукт

Отдельный опыт передаёт модели короткие фрагменты заранее выбранных страниц:
он исключает промах FTS и показывает поведение реранкера при доступных фактах.
Сравнивались текущий промпт и экспериментальный, требующий подтверждения всех
ограничений и запрещающий выполнять команды из текста страниц. Меняется
промпт целиком; эффект отдельной фразы этим опытом не изолирован.

| Метрика | Текущий | Экспериментальный строгий |
| --- | ---: | ---: |
| Выбор подходящей страницы | 11/12 | 12/12 |
| Опыты с нарушением явных условий | 4/16 | 1/16 |
| Ложный ответ на отсутствующую тему | 0/4 | 2/4 |
| Невалидный формат ответа | 0/16 | 2/16 |
| Реранк, медиана | 247 мс | 227 мс |

Строгий вариант помог с языком и отрицаниями, но для «нейтринного телескопа»
выбрал Prius, для Honda Civic — Corolla. При обратном порядке на обоих
отрицательных вопросах ответил «Нет» вместо пустой строки: штатный парсер
обоснованно отвергает такой формат. В продукте это вызвало бы запасную выдачу,
а не корректное отсутствие результатов. Поэтому уменьшение числа известных
нарушений здесь не означает улучшения поиска в целом.

Текущий реранкер на полном наборе кандидатов в обоих проходах смешал
пассивную изоляцию с активным шумоподавлением, Linux с Windows, работу без
интернета с облаком. На малой паре документов он иногда справился лучше.
Следовательно, следующие проверки должны использовать реальные полные
наборы и отрицательные запросы, а не только удобные пары.

## Границы, которые один промпт не исправит

Отдельный стенд без инференса воспроизвёл три сценария:

1. **Нужная страница вытесняется бюджетом.** Восемь лексических посещений без
   извлечённого текста и двенадцать FTS-страниц заполнили исходные 20 мест.
   Дополнительный запрос действительно нашёл нужную страницу, объединение
   содержало 21, но `slice(0,20)` исключил её. Это проблема пробной схемы
   расширения, которая пока не подключена к продукту. Простое дописывание
   кандидатов в конец нельзя использовать при интеграции.
2. **Индексация ограничена.** В исходнике на 16 531 символ контрольная фраза
   находится на позиции 16 500. После штатного чанкинга осталось восемь
   фрагментов без неё; настоящий сборщик вернул ноль кандидатов. «Любая
   информация, которую читал пользователь» пока не гарантируется. Нельзя
   исправить это бесконтрольным увеличением объёма индекса: потребуется
   отдельный замер хранения и фоновой нагрузки.
3. **Пустой ответ ИИ не всегда означает пустую выдачу.** Штатная политика
   возвращает точные лексические совпадения даже при пустом списке реранкера,
   с `degraded:false`. Проверка намеренно подменяла реранкер на `[]` только
   внутри временного процесса и восстановила его после вызова; реальное
   качество модели этим сценарием не измерялось. Такой fallback может быть
   полезен для навигации, но для строгого смыслового запроса пользователь
   должен понимать, что страницу ИИ не подтвердил.

## Что делать следующим шагом

Сначала сохранить отрицательные случаи как критерий качества и проверить
способ явно возвращать «ничего не подходит» без сломанного формата. Проверять
это на сохранённых полных наборах кандидатов, включая перестановки и отсутствие
нужной страницы. Строгий промпт из этого отчёта и автоматический переход на
один вариант отклонены результатами проверки.

Затем проверить ограниченное распределение мест между исходными кандидатами
и расширением: максимум 20 остаётся, полезный новый источник получает место,
точные совпадения не теряются. Это изменение только диагностического стенда,
до включения в браузер. После качества — нагрузочный опыт с большой историей,
записью индекса, AI-очередью и отменой запросов. Увеличение индекса и возврат
эмбеддингов текущими результатами не обоснованы.

## Воспроизведение и проверки

- `node scripts/history-semantic-deep.mjs` — модель, временная база, полный прогон.
- `node scripts/history-semantic-deep.mjs --summarize` — пересчёт метрик без модели.
- `node scripts/history-semantic-boundaries.mjs` — три граничных сценария без AI.
- `history-semantic-deep.json` — варианты, видимые модели фрагменты, ответы и времена.
- `history-semantic-boundaries.json` — исходы граничных проверок.

Синтаксис трёх новых скриптов, `npm run build` и типы обоих таргетов прошли.
Проверка границ завершилась всеми утверждениями; модельный стенд проверяет
целостность прогона, а обнаруженные ошибки качества сохраняет в отчёте.
Полный `npm test` не повторялся: продуктовые исходники не менялись. Из прошлого
этапа остаются семь нарушений размеров файлов и непостоянный DOM-таймаут
UI-стенда истории, описанные в `history-numeric-validation.md`.
Коммит выполняется с `core.hooksPath=NUL`: обязательные проверки сделаны
отдельно, известные провалы полного набора не скрываются.
